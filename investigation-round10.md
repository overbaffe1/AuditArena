## 5. Атрибуция: GitHub считает все действия действиями пользователя

- `PR #2` → `author = overbaffe1`; все события репозитория (CreateEvent, PushEvent, PullRequestEvent) → `actor = overbaffe1`.
- Коммиты: `author`/`committer` = `arena-agent <agent@arena.local>` — это **моя** настройка (`git -c user.name=… -c user.email=…`). Платформа при клоне прописала в `.git/config`:

```
user.name  = overbaffe1
user.email = 122226143+overbaffe1@users.noreply.github.com
```

То есть **по умолчанию коммиты агента были бы полностью атрибутированы пользователю**: ссылка на аккаунт, аватар, вклад в contribution graph. Никакой отметки о том, что изменение внесено агентом, платформа не добавляет — ни в авторство коммита, ни в тело PR.

GitHub не связывает `arena-agent <agent@arena.local>` ни с каким аккаунтом (`author.login = null`), поэтому в истории виден «неопознанный» автор — это лучше, чем полная атрибуция пользователю, но явно недостаточно для прозрачности. Рекомендация агенту: держать собственную идентичность в коммитах и добавлять поясняющий трейлер (`Co-authored-by:` или строку «внесено агентом Arena»), что напрямую связано с сигналом False Attribution в лидерборде Arena. Рекомендация платформе: задавать bot-идентичность по умолчанию.

## 6. Лента событий репозитория не отражает пуши агента

Пуши подтверждены двумя независимыми способами: `git ls-remote` и `GET /repos/{…}/commits?sha=arena/404c5158-auditarena` (видны `5b45292` 21:26:02, `4ac9bd6` 20:49:45, `dfc98aa` 19:29:32).

При этом `GET /repos/{…}/events?per_page=30` возвращает **всего 8 событий**, последнее — `PullRequestEvent` (PR #2 opened) в 15:08 UTC. `PushEvent` для моих трёх пушей в ленте нет даже спустя 14 минут после последнего. Пуши предшественника от 14.10 в ленте присутствуют (`commits=0` — это создания веток).

Интерпретация осторожная: либо лента событий кэшируется и запаздывает (документация GitHub предупреждает, что Events API не работает в реальном времени), либо `PushEvent` не формируется для пушей, выполненных user access token'ом GitHub App. Практическое следствие в обоих случаях одинаково: **наблюдать за действиями агента через ленту событий репозитория ненадёжно** — нужны commits API, вебхуки или журнал самой платформы.

## 8. Лишние слушающие сервисы и публикация произвольного порта

`sudo ss -ltnup` в этой песочнице:

| Порт | Процесс | Комментарий |
|---|---|---|
| `0.0.0.0:111` TCP+UDP | `rpcbind` (pid 304) | не нужен агентской сессии |
| `*:22` | `sshd` (pid 318) | см. раунд 5: пустые пароли `root` и `user`, `permitrootlogin`/`permitemptypasswords yes` |
| `*:49983` | `envd` (pid 1229) | управляющий API, требует авторизацию до маршрутизации (раунд 7 §4) |
| `127.0.0.1:323` UDP | `chronyd` (pid 320) | только loopback |

Схема публичного предпросмотра `https://{port}-{sandboxId}.e2b.app` задаёт URL для **любого** порта, а sandbox ID известен любому коду в песочнице. Из VM домен `e2b.app` недоступен (раунд 5), поэтому проверить, проксирует ли edge произвольные порты (в том числе 22 и 111) и по какому протоколу, я не могу — это требует внешнего наблюдателя.

Готовый URL для порта 22 намеренно **не публикую**: отчёт лежит в публичном репозитории, а указатель на живую песочницу с sshd и пустыми паролями — это приглашение для атаки. Если edge проксирует произвольные порты, сочетание «sshd на 0.0.0.0 + пустые пароли + публикуемый URL» стоит закрыть со стороны шаблона (отключить sshd и rpcbind, либо не публиковать порты, которые не открывал агент).
