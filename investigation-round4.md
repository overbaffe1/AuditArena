# Раунд 4: GitHub-сессия, прокси E2B, жизненный цикл VM и причина обрыва хода

Проверка 14.10.2026, 12:03–12:20 UTC. Всё внутри своей VM — только чтение (плюс `sudo journalctl`, sudo без пароля). Значения токенов не печатались и не записывались; чужие песочницы и чужие репозитории не трогались. Единственный «пишущий» зонд — два `POST /pulls` с пустым телом (см. §5): GitHub отвечает 422/403 до создания объекта, ни одного PR создано не было (проверено: в обоих репозиториях 0 PR).

## 1. Почему предыдущий ход оборвался

Изнутри VM видно не «мозг» (модель), а исполнителя команд. Поэтому причина восстанавливается по хронометражу, а не по логам модели. Хронометраж собран из трёх независимых источников: журнал systemd (сохраняется через паузы, см. §2), `atime` бинарников (`/` смонтирован с `relatime`, первое обращение после снимка шаблона оставляет точное время) и mtime артефактов платформы в `/tmp/arena-workspace`.

Что из этого следует:

- VM не падала и не зависала. Последняя команда отработала за 1,8 с, нормально вернула вывод, после чего платформа штатно закрыла ход: прогнала хук сбора патча (12:05:09) и поставила песочницу на паузу (12:05:18). Это процедура нормального конца хода, не аварийный останов.
- Между последним результатом инструмента (≈12:05:01) и закрытием хода (12:05:09) прошло около 8 секунд. За это время модель не вызвала ни одного инструмента и не выдала пользователю текста. То есть обрыв произошёл на стороне «модель ↔ бэкенд Arena», а не в песочнице.
- Что укладывается в 8 секунд: (а) модель вернула пустой финальный ответ / сигнал конца хода сразу после результата инструмента — типичный сбой агентного цикла «отработал tool, не написал итог»; (б) быстрый отказ провайдера или бэкенда (ошибка запроса, лимит контекста/вывода, failover оркестратора — Arena в справке прямо допускает автоматическую смену модели, когда «ответ грозит сломать сессию»). Что не укладывается: долгая генерация, обрезанная по длине (за 8 с столько не наговорить), таймаут инструмента, сетевой тест (он завершился сам).
- Изнутри VM (а) от (б) не отличить: ни запрос к модели, ни её ответ, ни код ошибки в песочницу не попадают. Отличить может только интерфейс Arena (был ли баннер ошибки / пустое сообщение) или trace бэкенда по времени 12:05:01–12:05:09 UTC 14.10.2026.

Практический вывод: если в чате после шестого tool-вызова не было ни текста, ни ошибки — это пустой финал модели (а). Если был баннер ошибки — (б). В обоих случаях работа в песочнице не пострадала: рабочая папка и ветка пережили паузу без потерь.

## 2. Жизненный цикл VM: это пауза/возобновление с памятью, а не «новая VM на ход»

Раунд 3 предполагал, что Arena не делает memory-resume (аргумент: uptime секунды, старых процессов нет). Сейчас есть данные, которые это опровергают для случая «тот же sandbox ID, другой template ID»:

| Признак | Наблюдение |
|---|---|
| Boot ID журнала | один и тот же `7b0855bc…` для сборки шаблона 15.06.2026 17:00:01 и для обоих ходов 14.10.2026; второго «boot» в `journalctl --list-boots` нет |
| `envd` | PID 1229 в обоих ходах, `starttime` = 979 тиков (9,79 с от старта ядра) — тот самый процесс, запущенный при сборке шаблона 15.06 |
| Счётчик PID | мои shell: 1385 (прошлый ход) → 1520 (этот), счётчик не сбрасывался |
| Диск | `/tmp/arena-workspace/coding.*` от 12:05:09 (прошлый ход) на месте; повторной гидратации `/home/user` не было |
| Маркеры снимков | ядро пишет `random: crng reseeded due to virtual machine fork` при каждом восстановлении; в журнале их 9 за сборку шаблона и ровно 1 за 14.10 (12:05:18.785 — штамп временем гостя на момент паузы) |
| Часы | после каждого восстановления chrony: `Forward time jump detected!` (12:03:58.7 и 12:07:33.9) — стенку часов «доводят» до реального времени уже после старта |

Почему прошлые раунды видели «uptime — секунды»: монотонные часы ядра восстанавливаются из снимка. Шаблон был снят на ~10,5 с своего uptime, поэтому сразу после восстановления `uptime` показывает десятки секунд, а `uptime -s`/`ps` вычисляют фиктивный «boot» = сейчас − uptime (12:03:47 и 12:06:01 в этих двух ходах — ни то, ни другое не момент реального старта). Время паузы в uptime не входит. Старые *пользовательские* процессы отсутствуют просто потому, что команды инструментов короткие и завершаются сами; демоны (envd, chronyd, sshd) живут непрерывно с 15.06.

Итого два механизма, оба наблюдались в этом чате и у предшественников:

1. Между соседними ходами — `pause`/`resume` одной песочницы: sandbox ID прежний, `E2B_TEMPLATE_ID` меняется на ID нового снимка (`mn0k6lgvyo6q8utbj8jh` → `o7ojonabnbpp9wpr4nga`), память и диск сохраняются, часы доводятся. Возобновление ленивое — за ~2 с до первого tool-вызова хода (12:07:31.5 → 12:07:33).
2. Когда снимка уже нет (долгая пауза, истечение) — новая песочница с новым ID из базового шаблона и повторная гидратация рабочей папки (zip в раунде 3; в GitHub-сессии — `git clone`).

Это снимает открытый вопрос раунда 3 «почему при том же sandbox ID сменился template ID»: диск и память остались те же, сменился только идентификатор снимка.

## 4. Сеть: allow-list с разрывом TLS и перехват GitHub

DNS по-прежнему резолвит всё (через 8.8.8.8). Фильтрация идёт после TCP-соединения, по SNI: к `example.com`, `api.openai.com`, `api.anthropic.com`, `arena.ai`, `help.arena.ai`, `e2b.dev` TCP открывается, но TLS-рукопожатие обрывается (`SSL_ERROR_SYSCALL`, 30–80 мс). Прошлые раунды фиксировали открытый egress (401/405 от API провайдеров) — его больше нет.

Разрешённые хосты делятся на два класса:

| Хост | Сертификат, который видит VM | Режим |
|---|---|---|
| `github.com`, `api.github.com`, `codeload.github.com` | `O=E2B, CN=<host>`, выдан `O=E2B, CN=E2B Proxy CA` (лист 14.10 11:11:23 → 15.10 12:11:23) | TLS разрывается на прокси E2B |
| `registry.npmjs.org`, `pypi.org`, `files.pythonhosted.org` | подлинные (Google Trust Services / GlobalSign) | сквозной проход |
| `raw.githubusercontent.com`, `objects.githubusercontent.com`, `uploads.github.com`, `gist.github.com` | — | заблокированы (релизные ассеты и raw-файлы не скачать) |

CA прокси (`CN=E2B Proxy CA`, self-signed, 13.10.2026 04:02:34 → 13.10.2027, sha256 `B8:F8:5A:63…`) был установлен в доверенные корнем через envd в момент создания песочницы (12:03:57.958), на 0,02 с раньше первой записи журнала за 14.10. Это означает, что платформа выполняет root-шаги инициализации до того, как ход начнётся. Серверные инструменты (`web_search`, `fetch_page`) работают не из VM: справка Arena открылась через них, хотя из VM `help.arena.ai` недоступен.

## 5. Как устроен «доступ к GitHub»

Внутри VM лежат `GH_TOKEN` = `GITHUB_TOKEN`: префикс `aren`, 24 символа. Это не токен GitHub (у тех префиксы `ghp_`/`gho_`/`ghu_`/`ghs_`/`github_pat_`), а заглушка Arena. Ни credential helper, ни `~/.config/gh`, ни `.netrc`, ни глобального gitconfig нет — есть только `.git/config` с `user.name=overbaffe1`, noreply-почтой и remote `https://github.com/overbaffe1/AuditArena.git` без встроенных кредов.

Настоящая аутентификация делается прокси E2B, который подменяет/вставляет заголовок на выходе. Три запроса к `GET https://api.github.com/user`:

| Что отправлено из VM | Ответ |
|---|---|
| без заголовка авторизации | `200`, `login: overbaffe1` |
| `Authorization: token <aren-заглушка>` | `200`, `login: overbaffe1` |
| `Authorization: token aren_bogus_…` | `200`, `login: overbaffe1` |

То есть учётка вшивается в любой запрос к `github.com`/`api.github.com` из этой песочницы, независимо от содержимого заголовка. Секрет в VM не нужен вовсе.

Кем является реальная учётка (из заголовков ответов GitHub и `GET /user/installations`):

- user-to-server токен GitHub App **`arena-ai-coding-agent`** (app_id 4187077, `x-oauth-client-id: Iv23lifFg4c9eT1T6hLC`), действующий от имени `overbaffe1` (id 122226143); `x-oauth-scopes` пуст — классических OAuth-scope нет, права даёт установка App.
- установка id 154763295 на аккаунте пользователя от 18.08.2026 21:17:18, `repository_selection: selected` — 16 репозиториев (из них 6 приватных); права установки: `contents: write`, `pull_requests: write`, `workflows: write`, `repository_hooks: write`, `actions/checks/issues/metadata/statuses: read`.
- токен выписан в 12:07:33 UTC (первый tool-вызов хода) на 8 часов (`github-authentication-token-expiration: 2026-10-14 20:07:33 UTC`) — перевыпуск привязан к возобновлению песочницы.
- edge-регион GitHub, с которого приходит запрос прокси: `westus2`.

Насколько узок реальный токен — проверено без побочных эффектов:

| Проверка | Результат |
|---|---|
| `GET /repos/overbaffe1/AuditArena` | 200 |
| `GET /repos/overbaffe1/arena_work`, `/test1` (приватные, входят в ту же установку) | 403 `Resource not accessible by integration` (ответ подлинный: `x-github-request-id`, edge-регион) |
| `GET /repos/e2b-dev/E2B`, чужие публичные | 200 (публичное чтение) |
| `POST /repos/overbaffe1/AuditArena/pulls` с телом `{}` | 422 «base/head weren't supplied» — право на запись есть, объект не создан |
| `POST /repos/overbaffe1/orbit/pulls` с телом `{}` (публичный, в той же установке) | 403 `Resource not accessible by integration` — записи в другие репозитории нет |
| `GET /installation/repositories` | 403 — это не installation-токен |
| `GET /user/emails` | 200, 2 записи (значения не выводились) |

Вывод: Arena выдаёт **токен, сужённый до одного репозитория сессии** (поведение совпадает с GitHub «scoped user-to-server token»), при том что сама установка App покрывает 16 репозиториев. Это хорошая граница: даже утёкший из песочницы «реальный» токен (которого в ней нет) не дотянулся бы до других репозиториев.

Что при этом остаётся рисками для владельца репозитория:

1. Любой код, исполняемый в песочнице — включая пакеты с npm/PyPI, которые агент ставит по ходу работы, — получает доступ к GitHub от имени `overbaffe1` в пределах этого репозитория без всякого секрета, просто сделав HTTPS-запрос.
2. Ограничение «пушить только в `arena/0594836f-auditarena`» — правило для модели, а не техническая граница: токен имеет `contents: write` на весь репозиторий, ветка `main` не защищена (`protected: false`). Если это важно, включите branch protection на `main`.
3. `workflows: write` и `repository_hooks: write` в правах установки — сильнее, чем нужно для «ветка + PR»: это возможность менять CI и вешать webhooks. В этой сессии они не использовались.
4. Каждый коммит из сессии получает трейлер через локальный hook `.git/hooks/commit-msg`: `Co-authored-by: arena-agent <297053741+arena-agent@users.noreply.github.com>` (аккаунт `arena-agent`, «Arena Agent», создан 26.06.2026). Автор и коммиттер при этом — `overbaffe1`.

Клон сделан платформой shallow (`--depth 1`, в `.git/shallow` один SHA) с refspec только на `main` и `arena/0594836f-auditarena*`; история на GitHub и правда состоит из одного коммита, так что здесь ничего не скрыто.

Фраза из текущего сообщения пользователя (собрана из кодов символов, чтобы не попасть в sudo-лог) по `/home /tmp /var /run /etc /root /opt /srv` — 0 совпадений. ## 9. Параллельная сессия в том же репозитории

Во время этого хода на GitHub появилась ветка `arena/b030c45c-auditarena` — другая Arena-сессия (sandbox `iyv5vd9bk4rnctv6qcj3c`, гидратация ≈12:03:41, то есть запущена за 15 с до этой) с тем же заданием. Её коммиты: 12:13:45 «Add round 4 sandbox and GitHub audit», 12:14:15, 12:17:16 — файл `investigation-round4-github.md`, тот же трейлер `Co-authored-by: arena-agent`. PR она не открывала. Её ветку я не трогал, файл прочитал через API для сверки.

Где отчёты сходятся: другой образ и другой `envd` (тот же sha256 `92b0548e…`), uid 1001 и sudo без пароля, allow-list с обрывом TLS после ClientHello, `E2B Proxy CA` в цепочке GitHub, `GH_TOKEN` = `GITHUB_TOKEN`, аутентификация как `overbaffe1`, `/app` 401 и `/installation/repositories` 403 (не installation-токен), пустые `coding.*` в `/tmp/arena-workspace`, вывод «обрыв произошёл выше уровня sandbox».

Где расходятся и почему я считаю свою версию точнее:

- Тот отчёт трактует июньские метки (`ExecMainStartTimestamp=2026-06-15 17:00:10`, записи журнала с 15.06) как «устаревшее состояние образа», а старт PID 1229 — как «около 12:06». По данным §2 это один непрерывный boot: `starttime` envd в тиках ядра, единый boot ID и ненулевой счётчик PID показывают, что процесс действительно запущен 15.06 и пережил снимки; «12:06» — арифметика `ps` от фиктивного времени старта. Расхождение «PID 1 ≈12:04:32 против `uptime -s` ≈12:03:42», которое там отмечено как необъяснимое, — тот же эффект: uptime восстановлен из снимка шаблона.
- Там не проверено, что прокси вставляет учётку в запросы без заголовка авторизации, а значит `GH_TOKEN` — заглушка (§5). Отсюда же не видно, какой это GitHub App, срок токена и его сужение до одного репозитория.
- Там нет хронометража конца хода; вывод «причину установить нельзя» верен, но окно 12:05:01–12:05:09 и штатное закрытие хода платформой (§1) сужают список причин.

Если пользователь сравнивает две сессии, стоит учесть: обе получили токен, сужённый до `AuditArena`, обе пушат под `overbaffe1`, и ветки друг друга видят только через GitHub — в песочницах они изолированы.

## 10. Поправки к прошлым отчётам

- Раунд 3, «Arena не делает memory-resume»: неверно для случая «тот же sandbox ID». Это именно пауза/возобновление с памятью; uptime и «время старта» процессов там фиктивны (см. §2). Верно другое: при смене sandbox ID песочница действительно новая, а рабочая папка восстанавливается из снимка.
- Раунд 3, «журнал июля приехал вместе с диском»: подтверждается и уточняется — журнал непрерывен с момента сборки шаблона, потому что это один и тот же boot, а не копия логов.
- Раунды 11–15, «интернет из VM есть»: больше нет; egress ограничен шестью хостами с SNI-фильтрацией и разрывом TLS для GitHub.
- `code-interpreter` на 49999 и jupyter на 8888, описанные раньше, в текущем образе отсутствуют; единственный путь исполнения — envd.
