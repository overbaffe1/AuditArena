## Главный результат: серверная сторона live-tail'ит файлы workspace

Сниффер рев.2 за 101 с снял 2533 HTTP-записи, из них 1171 `Filesystem/Stat` и
50 `GET /files`, не связанных ни с одним моим вызовом инструмента:

| Файл в корне репо | Stat | GET /files | Поведение |
| --- | --- | --- | --- |
| `.envd-wire17.log` (создан в ходе) | 576 | 18 | первый GET через 0.22 с после CREATE; tail с каденсом 0.254 с, пока файл пишется |
| `.arena-watch-rev6.log` | 573 | 31 | всплески по 3–4 GET каждые ~10 с |
| `.envd-children2.log` | 21 | 0 | пишется редко → почти не дёргается |
| `.aaa-probe17.log` (создан нарочно) | 1 | 1 | GET через 0.22 с после создания |

Механизм: серверная эвристика наблюдает за dot-файлами `*.log` в корне
workspace и непрерывно читает их через envd (`Stat` до 5.7 раз/с на горячий
файл, `GET /files` по изменению). Частота привязана к churn mtime: активно
пишущийся файл tail'ится каждые ~0.25 с, редкий — почти не дёргается. Содержимое
уходит на хост тем же plaintext-каналом (риск №35).

Следствия: (1) аномалия раунда 16 (два `GET /files` на журнал наблюдателя во
время startup-зондов) объяснена — это тот же live-tail, а не чтение «лога
процесса»; (2) любой файл, попавший под эвристику, уходит на серверную сторону
без вызова инструмента модели — методологическое правило: не писать секреты и
токены в `*.log` в корне репо даже временно; (3) это же означает, что мои
журналы наблюдения платформа видит в почти реальном времени.

## Внешний агент: GitHub Actions заблокирован дважды

Вопрос пользователя «можешь ли ты сам вызывать агентов» проверен на Actions:

1. Push файла `.github/workflows/arena-probe17.yml` в ветку сессии — успешен
   (permission `workflows` позволяет править файлы workflow).
2. `gh workflow run arena-probe17.yml --ref arena/404c5158-auditarena` →
   `HTTP 404`: workflow регистрируется GitHub только из default branch
   (`main`), в которую мне пушить нельзя.
3. `POST /actions/workflows/arena-probe17.yml/dispatches` с ref ветки →
   `403 Resource not accessible by integration`: у установки приложения Arena
   нет permission `actions`.

Вывод: агент может приготовить workflow, но не активировать и не запустить его
без merge в `main` — то есть без шага человека (PR-флоу). Поправка к раунду 10:
`workflows:write` ≠ `actions:write`; «путь к Actions» перекрыт merge-гейтом.
Файл workflow удалён из дерева в этом же ходе (в истории коммитов остался как
доказательство); при merge PR #2 он бы активировался, поэтому не оставлен.

## Поправки к прошлым отчётам

1. **Раунд 16, аномалия `GET /files .arena-watch-rev6.log`** — объяснена:
   серверный live-tail dot-`*.log`, а не эвристика «лога процесса».
2. **Раунд 10, риск «workflows:write → путь к Actions»** — уточнён: push файла
   workflow возможен, запуск нет (404 реестра вне main + 403 на dispatch);
   активация требует merge, то есть действия человека.
3. **Процедура лечения отката** — дополнена: голый `git fetch` в свежем клоне
   даёт `FETCH_HEAD=main`; ветку сессии.fetch'ить явно.
4. **Методика редактации** — моя же регулярка `arena-[A-Za-z0-9_\-]{6,}`
   съела подстроку имени `.arena-watch-rev6.log` в телах Stat (в отчёте путь
   виден как `.<REDACTED len=16 …>.log`). Урок: редактацию применять к значениям
   полей, а не к сырому тексту тела; секретов она при этом не пропустила
   (231 метка — все от имён файлов, не от токенов).

## Что всё ещё не видно отсюда

* Тела `Process/Start` не снялись (вероятно, chunked TE у connect-rpc): схема
   конфигурации процесса (envs, cwd, user) и путь инжекции `GH_TOKEN`
   (через `/init` или через Start) неизвестны; шанс снять тело `/init` даст
   resume в раунде 18 (сниффер оставлен).
* Полное правило выбора файлов для live-tail: наблюдались только dot-`*.log`
   корня репо; поведение для подкаталогов и иных расширений не проверено.
* Куда серверная сторона девает прочитанное (UI-панель, хранение) — вне гостя.
* Реестр коннекторов по-прежнему не перечислим целиком.
