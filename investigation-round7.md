- лимит непрерывной работы: Hobby — 1 ч, Pro — 24 ч; пауза и возобновление сбрасывают этот таймер.

Сопоставление с наблюдениями: Arena использует паузу с сохранением памяти (в раунде 6 процессы пережили паузу — значит, не «filesystem-only» режим) и возобновление по следующему ходу. Но исчезновение снимка через 3,5 часа **не объясняется** правилами E2B — paused-песочницы не истекают. Значит, снимок убивает сама Arena (своя политика удержания) либо при долгом простое выбирает другой сценарий. Граница по нашим данным: 2 минуты — жив, 3,5 часа — нет.

Что из этого следует:

- Вершина моей ветки на GitHub (`43f1688`, коммиты раундов 5–6) при старте **не подтягивается**: локальная ветка указывает на базу сессии `7f14bf3`, remote-tracking ref `origin/arena/404c5158-auditarena` не создан, хотя refspec в `.git/config` его описывает. В `.git/shallow` — только `59f0a99` и `7f14bf3`.
- Актуальные файлы рабочая папка получает **не из git**, а отдельной записью платформы (два файла с одинаковым наносекундным штампом). Целостность проверена: `git hash-object` файлов на диске совпал с блобами вершины remote байт-в-байт (`e765b98…` и `c376d04…`).
- Итоговое состояние: **локальная история отстала от remote, а рабочее дерево актуально**. Файлы раундов 5–6 лежали как `?? untracked`, `git diff 7f14bf3..HEAD` пуст, а `git push --dry-run` вернул `! [rejected] … (fetch first)` — классический non-fast-forward.
- **Риск.** В этой ситуации агент, который «просто хочет запушить», может решить проблему силовым пушем. `git push --force` затёр бы на GitHub коммиты раундов 5–6 и историю PR #2. Я так не делал; корректная последовательность (выполнена): `git fetch --depth 5 origin arena/404c5158-auditarena` → `git reset --mixed FETCH_HEAD` (ветка на вершину remote, рабочее дерево не трогается) → дальше обычные коммиты и fast-forward push. После reset файлы раундов 5–6 перестали быть untracked и совпали с HEAD.
- Мелочь, но полезно знать: после пересоздания песочницы теряются и другие локальные состояния git — `.git/index`, `.git/info/exclude`, reflog; хук `commit-msg` платформа ставит заново (текст тот же, 208 Б).

## 3. Входящая поверхность: как платформа проверяет новый порт

Поднял HTTP-сервер на `0.0.0.0:8080` через `start_process`. Платформа отреагировала через 0,6 с — и сделала это **внутри песочницы**, чем объясняется механизм `warnings` про «host/origin rejection» и «iframe-embedding block»:

```
/bin/bash -l -c curl_status=0; curl -s -D '/tmp/.arena-hostcheck-headers-8080' -o '/tmp/.arena-hostcheck-8080' \
  -w '%{http_code}' -m 4 -H 'Host: 8080-i7zpv0j70s2ypzggfmyzb.e2b.app' http://127.0.0.1:8080/ || curl_status=$?; \
  echo; echo ===ARENA_HC_HEADERS===; head -c 600 '/tmp/.arena-hostcheck-headers-8080' 2>/dev/null; \
  echo ===ARENA_HC_HEADERS===; head -c 300 '/tmp/.arena-hostcheck-8080' 2>/dev/null; exit "$curl_status"
```

Мой сервер записал тот же запрос с другой стороны: `GET /` от `127.0.0.1:44240`, `Host: 8080-i7zpv0j70s2ypzggfmyzb.e2b.app`, `User-Agent: curl/7.88.1`; время совпало (19:23:34,432 — запуск скрипта, 19:23:34,438 — запрос в логе сервера). Артефакты проверки остаются в `/tmp`: `.arena-hostcheck-headers-8080` (162 Б, заголовки ответа) и `.arena-hostcheck-8080` (24 Б, первые 300 байт тела).

Выводы:

- Публичный URL предпросмотра — `https://{port}-{sandboxId}.e2b.app`, и **sandbox ID известен любому коду в песочнице** (`env`, `/run/e2b/.E2B_SANDBOX_ID`). Значит, любой процесс может узнать свой публичный адрес и передать его наружу (через разрешённые хосты или DNS — раунд 5 §6).
- Из VM `e2b.app` недоступен (раунд 5): песочница не видит собственный предпросмотр. Входящих соединений извне за этот ход не было — только локальный host-check.
- Сам факт: **входящая поверхность появляется автоматически**, как только любой процесс открыл слушающий порт. Это штатная функция (dev-сервер), но инициатива исходит от кода в песочнице, а не от пользователя.

## 4. API envd: один открытый эндпоинт и одна утечка схемы авторизации

Обход 41 пути на `127.0.0.1:49983`:

| Ответ | Пути |
|---|---|
| `204` без авторизации | `/health` |
| `401` `unauthorized access, please provide a valid access token or method signing if supported` | все остальные 39, включая заведомо несуществующие `/sandboxes`, `/kill`, `/snapshot`, `/debug/pprof`, `/v2`, `/openapi.json` |
| `401` **`missing signature query parameter`** | `/files` |

Два вывода. (1) Авторизация проверяется **до маршрутизации**, поэтому перечислить маршруты без токена нельзя — это правильная конструкция: 401 одинаков и для существующих, и для выдуманных путей. (2) `/files` — исключение: другой текст ошибки раскрывает и существование эндпоинта, и схему его авторизации (подпись в query-параметрах, тот самый «method signing» из общего сообщения). Эксплуатировать это без ключа подписи нельзя, но различие ответов — лишний канал информации об устройстве API.

Для полноты: `192.0.2.1` (`E2B_EVENTS_ADDRESS`) отвечает только на `/logs` (GET → 400 `method not allowed`), остальные пути → 404 (раунд 5 §4).

## 8. Риски: дополнение к списку раунда 5

К четырём пунктам раунда 5 §15 добавляются:

5. **Пересоздание песочницы рассинхронизирует git-состояние сессии**: локальная ветка на базе сессии, рабочая папка актуальна, push отклоняется как non-fast-forward. Само по себе не разрушительно, но провоцирует `push --force`, который стирает историю ветки и PR. Что делать: не форсить, а `git fetch origin <ветка>` + `git reset --mixed FETCH_HEAD`; владельцу репозитория — branch protection (она же блокирует force-push в защищённые ветки).
6. **Публикация порта происходит автоматически**: любой слушающий порт получает публичный URL `{port}-{sandboxId}.e2b.app`, а sandbox ID известен любому коду в VM. Процесс, который агент запустил (в том числе из зависимостей), может открыть порт и вынести URL наружу. Что делать платформе: подтверждение пользователя на публикацию порта или явный список опубликованных портов в интерфейсе.
7. **Различие текстов 401 у envd** выдаёт устройство API (`/files` + подпись в query) — мелочь, но бесплатно устранимая (§4).
