## 3. Что именно восстанавливается из снимка шаблона

Раунд 4 описал pause/resume живой песочницы. Теперь видно и «нулевую точку» — снимок самого шаблона.

- В журнале **два boot ID**: `a7c1d42f…` (486 записей, 15.06 16:59:21–17:00:00) и `7b0855bc…` (605 записей, 15.06 17:00:01 → сейчас). Шаблон собирали минимум в две стадии.
- Финальный снимок памяти сделан на **mono ≈ 10,10 с** boot `7b0855bc`. Доказательство: последняя июньская запись журнала — маркер форка (17:00:10.866, mono 10.1041), а первая сегодняшняя — mono 10.1767 (14:20:36.954). Разрыв **0,07 с монотонного времени при разрыве в 4 месяца реального**.
- Что успело произойти до снимка: `update-ca-certificates` (mono 9,784) → старт `envd.service` (mono 9,800, PID 1229) → `Startup finished in 423ms (kernel) + 9.376s (userspace)` → `passwd[1313]: password for 'user' changed by 'root'` (mono 9,978). Отсюда и «вечный» PID 1229: envd запущен при сборке шаблона и его состояние памяти копируется в каждую песочницу Arena.
- `dmesg` (кольцо в памяти) содержит только две записи `crng` — `init done` (mono 0,68) и маркер форка (mono 10,104). Журнал на диске содержит всю цепочку сборки: 8 маркеров форка с mono 10,53…28,49. Практическое правило: **журнал на диске — история всей линии шаблона, dmesg — история этой копии памяти**. Раунд 3 трактовал июньский журнал как «приехавший вместе с диском» — верно, но это не копия логов, а живой непрерывный boot.
- `/dev/sysgenid` (misc 126) — чтение **блокируется до следующего форка** (проверено: `timeout 3 dd if=/dev/sysgenid` → exit 124, ноль байт). Это источник маркеров `random: crng reseeded due to virtual machine fork`: CRNG пересевается на каждом форке, поэтому две песочницы из одного шаблона не делят состояние ГСЧ. Побочно: любой процесс в VM может детектировать момент паузы/возобновления, просто заблокировавшись на этом чтении.
- **Поправка к раунду 4.** Маркер форка появляется при возобновлении *живой* песочницы (pause→resume меняет genid — тот самый маркер «12:05:18.785» из раунда 4). При создании песочницы из базового шаблона нового маркера **нет**: genid уже учтён в снимке. В этом ходу маркеров за 16.10 — ноль.
- `/dev/userfaultfd` (misc 127) присутствует — согласуется с ленивой подачей страниц памяти при восстановлении (UFFD на стороне хоста), но изнутри VM не подтверждается.
- `/dev/snapshot` (misc 231) — штатный интерфейс swsusp (`/sys/power/state` = `disk`), к снапшотам E2B отношения не имеет. Не трогал.
- `/dev/vsock` есть, но управляющий канал — TCP: хост `10.12.0.44` держит 2 соединения к `envd:49983` (раунд 3 — `10.12.0.110`, раунд 4 — `10.12.0.120`: пул хостов, IP меняется). Соединения пересоздаются в пределах хода.

Насколько это опасно на практике. Песочница — Firecracker-VM с единственной сетью 169.254.0.21/30 и шлюзом-хостом; из интернета она не видна (входящих соединений нет, кроме хостовых к `envd:49983`). Значит поверхность — это всё, что уже находится в сети оркестратора: хост и, если между песочницами есть маршрутизация, соседние VM. Для них root в этой песочнице получается **без единого секрета**. Отдельно: одинаковые во всех песочницах SSH-ключи хоста делают бессмысленной проверку known_hosts для любого, кто подключается к ним изнутри инфраструктуры.

## 6. Сеть: политика вне гостя, граница проходит по SNI

- В госте **нет ни одного правила netfilter**: `iptables -S` (filter и nat) — только политики `ACCEPT`, `nft list ruleset` пуст. Фильтрация и перехват делаются вне VM: из песочницы их нельзя ни прочитать, ни изменить.
- Allow-list не изменился: проходят `github.com`, `api.github.com`, `codeload.github.com`, `registry.npmjs.org`, `pypi.org`, `files.pythonhosted.org`. Обрыв TLS после ClientHello (30–120 мс) для `raw.githubusercontent.com`, `objects.githubusercontent.com`, `uploads.github.com`, `gist.github.com`, `arena.ai`, `help.arena.ai`, `e2b.dev`, `api.openai.com`, `api.anthropic.com`, `example.com`, `google.com`.
- Порт 80 фильтруется так же: `http://github.com/` → 301, `http://pypi.org/` → 301, `http://example.com/` → обрыв за 12 мс.
- **Цель выбирается по SNI, а не по IP** (новое, раунд 4 это не проверял). Рукопожатия без передачи данных:

| IP назначения | SNI | Результат |
|---|---|---|
| `example.com` (104.20.23.154) | `github.com` | TLS OK, сертификат `O=E2B, CN=github.com` от `E2B Proxy CA` |
| `example.com` (104.20.23.154) | `pypi.org` | TLS OK, **подлинный** сертификат pypi.org (GlobalSign) |
| `github.com` (20.29.134.23) | `example.com` | обрыв (EOF сразу после ClientHello) |
| `pypi.org` (151.101.192.223) | `pypi.org` | TLS OK, подлинный сертификат |

  Вывод: прокси игнорирует IP, указанный клиентом, и соединяется с хостом из SNI. Allow-list нельзя обойти подменой IP (трафик всё равно уйдёт на разрешённый хост), но и «случайно» выйти наружу не получится. TCP-соединение при этом открывается к любому IP и порту (`1.1.1.1:53/80/443`, `github.com:22`) — его принимает прокси, а не цель; прикладной ответ приходит только от разрешённых.
- UDP работает только на 53 → 8.8.8.8; `1.1.1.1`, `9.9.9.9` и шлюз `169.254.0.22` по UDP/53 — таймаут. Резолвер зафиксирован жёстко.
- **Но DNS-имена не ограничены**: запрос A/TXT по произвольному имени уходит и получает ответ (проверено на `auditarena-probe-7f3e.example.com` → `answers=0`, то есть 8.8.8.8 сходил во внешний авторитетный NS). Это единственный канал из песочницы, не закрытый allow-list'ом: утечка в DNS-метках технически возможна для любого кода, который агент запустит. Доставку до конкретного внешнего NS я проверить не мог — своего домена нет, а чужие не использовал.
- Хост предпросмотра `49983-i0bpo1x9vjy04xcuymjvq.e2b.app` резолвится (34.102.227.47, GCP), но из VM недоступен (обрыв, 73 мс). Предпросмотр работает из браузера пользователя, не из песочницы.
- **CA прокси ротирован** с раунда 4: `O=E2B, CN=E2B Proxy CA`, notBefore 14.10.2026 21:58:53, notAfter 14.10.2027, sha256 `E0:A4:E7:54:…` (в раунде 4 — notBefore 13.10.2026 04:02:34, sha256 `B8:F8:5A:63:…`). Ставится в доверенные при создании каждой песочницы (§2).
- Листовые сертификаты чеканятся по требованию: `github.com` — notBefore 16.10 13:20:38, notAfter 17.10 14:20:38 (25 часов, минус час к моменту первого использования); `notAfter − 24ч` совпал с секундой `git clone` (14:20:38).

## 10. `/tmp/arena-workspace` — рабочая зона платформенных хуков (новое)

└── procs/<processId>/

## 15. Сводка рисков для владельца репозитория (по убыванию значимости)

1. **Любой код, исполняемый в песочнице, получает GitHub-доступ от имени `overbaffe1` в пределах `AuditArena` без секрета** — прокси вшивает учётку в любой запрос (§7). Права установки включают `contents:write`, `workflows:write`, `repository_hooks:write`; `main` без branch protection и без rulesets. Что делать: включить protection/ruleset на `main` (требуется `administration`, которого у токена сессии нет — значит, это действие владельца, а не агента) и сузить права установки App до `contents:write` + `pull_requests:write` — `workflows` и `hooks` для схемы «ветка + PR» не нужны.
2. **Root в песочнице достаётся бесплатно**: `sudo NOPASSWD`, пустые пароли `root`/`user`, sshd с `PermitEmptyPasswords`/`PermitRootLogin`, PAM `nullok` (§5). В связке с п.1 любой вредоносный пакет с npm/PyPI, который агент поставит по ходу работы, означает запись в ваш репозиторий от вашего имени. Что делать владельцу: исходить из того, что содержимое репозитория и зависимости, которые агент ставит, — это вектор, а не только результат; со стороны платформы — закрыть пустые пароли и отключить password-auth в образе.
3. **DNS не закрыт allow-list'ом**: произвольные имена резолвятся через 8.8.8.8 и доходят до внешних авторитетных NS (§6) — потенциальный канал утечки в DNS-метках для того же кода из п.1–2. Что делать платформе: собственный рекурсор с фильтрацией имён.
4. **Доверенный CA прокси E2B установлен в системное хранилище песочницы** (§4, §6): любой процесс в VM видит трафик к `github.com` расшифрованным, включая вшитую прокси аутентификацию. Формула «секретов в VM нет» верна, но доступ к GitHub есть у каждого процесса — это тот же п.1, только с другой стороны.
5. **Установка App шире сессии**: по данным раунда 4 она покрывает 16 репозиториев (6 приватных), хотя токен сужен до одного. Сужение держится (403 на приватные `arena_work`/`test1` в этом ходу подтверждены), но сама установка даёт больше, чем нужно одной сессии, и её состав менялся 15.10 (§7) — стоит перепроверить в настройках GitHub, какие репозитории в неё входят.
