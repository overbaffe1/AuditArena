## 3. Маршрут промта (реконструкция по наблюдениям)

1. Сообщение пользователя → фронтенд Arena.ai (вне VM; публичная
   инфраструктура платформы, по URL песочницы — GCP).
2. Бэкенд собирает контекст: системные инструкции + сжатая история диалога +
   описания инструментов + результаты предыдущих вызовов.
3. По официальной справке Arena, при старте нового Agent Mode чата случайно
   выбирается модель-оркестратор из доступных в Agent Arena; обычно она остаётся
   той же на протяжении диалога, но при риске неудачного ответа система может
   автоматически переключить модель. Справка говорит, что Agent Mode не
   показывает пользователю модель-оркестратор после отправки feedback. Это
   описание уровня сессии, а не доказательство конкретного выбора в этом чате;
   подробности — в приложениях A14–A15.
4. Если модель вызывает инструмент, платформа исполняет вызов в этой E2B-VM
   (sandbox i8f4b59uq9w4ngg75fda5) и возвращает результат в контекст.
5. Финальный текст модели уходит в чат.

Локального процесса модели в VM не обнаружено; по интерфейсу инструментов и
наблюдениям модельный backend/API находится вне области этой VM. Поэтому её
ID здесь не виден: отдельные анонимные GET подтверждают лишь сетевую
доступность публичных API-доменов, а короткие пассивные захваты не показывают
исходящих запросов VM к LLM API.

## A7. Маршрут сообщения — реконструкция и степень уверенности

Реконструируемая последовательность:

1. Пользователь отправляет сообщение в интерфейс Arena.ai.
2. Backend Arena формирует контекст модели: инструкции, историю диалога,
   описания инструментов и результаты прежних вызовов.
3. Backend направляет запрос одному из доступных провайдеров/моделей.
4. Если модель выдаёт вызов инструмента, платформа передаёт его в эту E2B-VM;
   VM возвращает результат, который добавляется к контексту.
5. Модель формирует ответ, который возвращается в чат.

Формирование серверного контекста и отправка Arena → provider (пп. 2–3) —
реконструкция по устройству Agent Mode, а не packet-level наблюдение: этот
межсерверный запрос не захватывался сниффером внутри VM. П. 4 подтверждается
работой инструмента: команды исполняются в VM, а результаты возвращаются в
диалоговый цикл. Финальный текст виден пользователю в чате, но внутренний
backend-трафик также не наблюдался из VM. Поэтому фраза «пользовательский промт
не попадает в VM» означает: исходный чат не найден в проверенных местах и не
передавался в VM как полный текст сообщения; модель при этом может передать
производную часть текста в явной команде инструмента.

Платформа может выбирать из пула моделей — в частности, Claude, ChatGPT,
Gemini, Grok, Qwen, Kimi и других. Из доступных агенту данных нельзя определить,
какая именно модель обслужила этот конкретный ход; самоописание модели не
является надёжной телеметрией.

## A8. Что установлено и что остаётся неизвестным

**Подтверждено в рамках доступных проверок:**

- локальная VM — среда выполнения инструментов; локального процесса или
  обнаружимого runtime модели не найдено;
- в проверенном окружении нет env-имени с model/provider ID;
- файлы/карты памяти/кэши, проверенные по указанным фильтрам, не содержат

- проверенные пользовательские фразы отсутствуют в перечисленных каталогах,
  а контрольная фраза из файлов агента находится;
- публичные API провайдеров достижимы из VM без авторизации, но это лишь
  egress-проверка, не свидетельство маршрута запросов Arena.

**Не установлено и не выводится из этих тестов:**

- точный provider и точный model ID для текущего ответа;
- внутренний alias/deployment ID и его соответствие публичному названию;
- происходило ли автоматическое переключение (fallback) модели именно в этом чате;
- регион, request/trace ID и содержимое серверного контекста после сборки;
- серверные логи, правила маршрутизации и политика хранения запросов;

### Что добавляет актуальная справка

Повторно прочитана [официальная статья How to use Agent Mode](https://help.arena.ai/articles/5432423882-how-to-use-agent-mode),
которая на момент просмотра показывала «Last updated 8 days ago». Помимо уже
зафиксированного правила назначения сессии, она разъясняет устройство оценки:

- Agent Mode работает с длинной «single-threaded» трассой одной сессии, а не с
  парой ответов для голосования, как в Battle.
- В справке описана методика **causal tracing**: сигналы извлекаются из трасс,
  а эффект модели оценивается относительно рандомизированного среднего
  оркестратора.
- Сводные сигналы включают подтверждение успеха, похвалу/жалобу,
  steerability, bash recovery и tool hallucination.
- Имя оркестратора, согласно той же статье, сейчас не раскрывается
  пользователю после feedback.

Следствие: Agent leaderboard — агрегированная оценка поведения моделей на
множестве сессий, а не публичный журнал, который сопоставляет конкретный чат с
конкретным model ID. Это согласуется с тем, что список кандидатов из A14 не
идентифицирует модель именно нашего диалога. В изученных публичных статьях не
описан пользовательский lookup по session ID, request ID или экспорту; это
фиксирует предел найденной документации, но не доказывает, что такие поля не
существуют во внутренних логах Arena.
