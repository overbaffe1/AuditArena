## 1. `POST /init` в середине сессии: ротация токена доступа

Единственный `/init` в окне сниффера (20:48:47–21:05:09, старая песочница):

```
21:04:09.559  10.12.0.122:39994 → 169.254.0.21:49983
X-Access-Token: sha512_12=f17e635d770f len=64   (действующий токен песочницы)
тело (connect-rpc envelope + JSON):
  accessToken   <REDACTED len=64 sha256_8=40984450>   ← НОВЫЙ токен
  caBundle      595 симв., 1 сертификат (см. раздел 2)
  cpuCount      2
  defaultUser   user
  hyperloopIP   192.0.2.1
  lifecycleID   b519d0af-8744-4b8d-9320-…
  timestamp     2026-10-17T21:04:09.527951507Z
```

Наблюдения:

- `/init` — не только boot-вызов: он приходит **в середине жизни песочницы** и доставляет новый `accessToken`. Это ротация. Триггер неизвестен: boot был в 20:45:51, ротация в +18 мин; событий платформы рядом не видно (в это время шёл мой `add_voice`-ход). Гипотезы: TTL токена, смена lifecycle-компоненты, ручной/автоматический refresh оркестратора.
- **Ротация «аддитивная»**: после 21:04:09 заголовки `X-Access-Token` вплоть до смерти песочницы (21:05:09) несли **старый** отпечаток `f17e635d770f` (6812 запросов, 20:48:47→21:05:09). Новый токен из тела так и не появился в проводе старой песочницы. То есть старый токен не отзывается мгновенно.
- `hyperloopIP` = 192.0.2.1 — тот же адрес, что в MMDS (`address`); «гиперлуп» = канал метрик/логов (`/metrics`, `POST /logs`).
- `lifecycleID` — UUID поколения жизненного цикла песочницы.

**Проверка согласованности в новой песочнице:** текущий wire-отпечаток `27ff613aaf62` (1761 запрос, 21:11:06→21:13:37) **совпадает** с `accessTokenHash` из MMDS (`sha512_12`). Цепочка «MMDS-hash = sha512(действующий токен) = заголовок запросов» подтверждена и после пересоздания.

## 2. `caBundle` в `/init` — канал доставки MITM-CA, и поколения CA расходятся

- CA из тела `/init`: `subject=O=E2B, CN=E2B Proxy CA`, serial `6343B8FAEC51BDC8AF6DB5ECA63939E0`, `notBefore=Oct 17 12:06:24 2026` (создан за ~9 ч до ротации).
- CA-файл в гостье `/usr/local/share/ca-certificates/e2b-ca.crt`: то же subject, но serial `739AEB619C866B20C0953937463416D8`, `notBefore=Oct 16 10:50:07 2026` — **другое поколение**.
- mtime файла = **21:09:56.706 = boot+10 с** новой песочницы: envd перезаписывает CA-файл при каждом старте (очевидно, из `caBundle` своего boot-`/init`, который мой сниффер не успел поймать — стартовал в 21:11:06).
- Фактическая цепочка TLS: `openssl s_client -connect github.com:443` → `issuer=O=E2B, CN=E2B Proxy CA`, верификация проходит (push работает). Значит прокси подписывает цепочкой того поколения, которое лежит в доверенном хранилище гостьи.

Итог: **MITM-CA генерируется на стороне хоста с временем жизни ~1 год, доставляется в гостью через `/init` (boot и ротации) и перезаписывает trust store**. Поколения, доставленные разным песочницам/в разное время, различаются (serial, notBefore). Каталог `/usr/local/share/ca-certificates/` имеет права 777 (мир-записываемый): гостьевой root-процесс может подменить CA-файл — перехватывать собственный трафик песочницы (кросс-тенантной угрозы это не создаёт, но снимает вопрос «кто контролирует траст в VM» — контролирует гость).

## 3. Правило live-tail: корень рабочей области, по одному `Stat`+`GET` на изменение

Эксперимент (75 с наблюдения, созданы 4 приманки):

| Файл | Stat | GET |
|---|---|---|
| `logs18/x18.log` (подкаталог) | 0 | 0 |
| `plain18.log` (корень, без точки, `.log`) | 1 | 1 |
| `.hidden18.txt` (корень, dot, не `.log`) | 1 | 1 |
| `/tmp/outside18.log` (вне workspace) | 0 | 0 |

За полное окно (22,5 мин, включая ход 17) наблюдались также: `investigation-round17.md` Stat×2/GET×1 (сразу после `write_file`), `coding.patch`/`coding.diff`/`coding-numstat.txt` GET×1 каждый (сразу после записи сборщиком в 21:05:09), каталог `audio` Stat×1 (после `generate_speech`).

**Правило:** серверная сторона реагирует на **события изменения файлов в корне рабочей области** (любое имя, любое расширение, dot или нет): один `Stat` + один `GET /files`. Файлы, меняющиеся непрерывно (журналы приборов), получают постоянный tail: `.envd-wire17.log` Stat×3393/GET×18, `.arena-watch-rev6.log` GET×163. Подкаталоги и пути вне workspace не читаются вовсе. Это синхронизация/индексация уровня корня (вероятно, для дерева файлов в UI и баз патчсета), а не глубокий скан.

Пиры в одном окне: `10.12.0.104` (6111 запросов), `10.12.0.122` (730), `10.12.0.54` (379) — минимум три хостовые компоненты опрашивают песочницу одновременно.

## 5. Риски (продолжение нумерации)

- **№38. Ротация токена envd не защищает от гостевого root.** `/init` (boot и ротации) идёт plaintext-проводом с заголовком и телом, которые sniff-доступны любому root-процессу в VM: новый `accessToken` и `caBundle` читаются в момент доставки. Плюс MMDS-hash действующего токена доступен всем. Ротация меняет только «окно жизни» украденного токена, но не устраняет его перехват в гостье.
- **№39. Trust store гостьи перезаписывается каждым `/init` и мир-записываем.** Каталог CA 777, файл перезаписывается при boot; CA — поколениями (~1 год валидности, разные serial у разных доставок). Гостьевой код может подменить CA и перехватывать TLS собственных процессов песочницы (например, читать `GH_TOKEN` из HTTPS-запросов git к github.com). Кросс-тенантной угрозы нет (трафик каждой песочницы изолирован её прокси), но внутри песочницы это путь от «world-writable python-пакетов» (риск №27) к полному перехвату секретов.
- **№36 (уточнение).** Live-tail читает из корня workspace **любой** изменённый файл один раз (`Stat`+`GET /files` от root, мимо DAC) и непрерывно tail-ит непрерывно меняющиеся. Файл в корне с чувствительным содержимым (даже с правами 600, даже dot, даже не `.log`) будет прочитан серверной стороной при первом изменении.
