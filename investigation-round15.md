## Поправки к прошлым отчётам

1. **Раунд 14, «место исполнения инструментов» — уточнено и усилено.** В VM
   исполняются только: python-программа `read_file` (2832–2963 симв., uid 1001)
   и bash-пробы/`mkdir -p` у `write_file`/`edit_file`. Сами данные читаются и
   пишутся внутри envd от root: чтение — `GET /files` (`download.go`:
   `os.Open(resolvedPath)` + `http.ServeContent`, без сброса привилегий),
   запись — `POST /files` (`upload.go`: `EnsureDirs` → pre-chown →
   `OpenFile(O_WRONLY|O_CREATE|O_TRUNC, 0o666)` → chown → `ReadFrom`).
   Доказательства: `read_file` вернул содержимое файла `root:root 600`, который
   uid 1001 открыть не может (`OSError 13`), причём `atime` файла обновился на
   53 мс **позже** завершения in-VM python; `edit_file` перезаписал тот же файл;
   setuid-бинарников в цепочке `/bin/sh → ionice → nice → bash → python3` нет.
2. **Раунд 14, «edit_file — три вилки за 135 мс» — уточнено.** Прямых детей envd
   у `edit_file` два (проба по компонентам + `mkdir -p`); «три вилки» — это
   цепочка обёртки `/bin/sh → ionice → nice → bash`, которую видел наблюдатель с
   периодом 10 мс.
3. **Раунд 14, риск №28 — усилен.** Login-shell (`/bin/bash -l -c`, читающий
   `~/.profile` → `~/.bashrc`) запускается не только зондом `ARENA_STATUS`, но и
   каждым файловым вызовом: на 8 вызовов `read_file` счётчик чтений показал
   `.bashrc|OPEN x21`, `.profile|OPEN x14`. Пользовательские файлы исполняются
   платформой при каждом обращении к инструменту.
4. **Раунд 10, «warnings не формируются» — шестое подтверждение при обоих
   задокументированных триггерах.** Сервер на 0.0.0.0:8097 отвечал 403 на чужой
   Host и слал `X-Frame-Options: DENY` + `Content-Security-Policy:
   frame-ancestors 'none'`; стартовый зонд платформы получил именно такой ответ
   (19:11:01.949, `ua=curl/7.88.1`, заголовки только Accept/Host/User-Agent), а
   поля `warnings` не появилось ни в `start_process`, ни в `get_process_output`.
5. **Раунды 12 и 14, записи cmdline `/usr/bin/envd` (13 симв.) — раскрыты.** Это
   не отдельные процессы демона, а снимки ребёнка между `fork` и `exec`: на
   0 мс uid=0 и cmdline `/usr/bin/envd` или пусто, на 2–3 мс обёртка
   `/bin/sh -c …oom_score_adj…`, на 5–10 мс целевая команда и uid=1001. То есть
   envd форкает от root, сбрасывает привилегии до uid 1001 и только потом
   исполняет команду.
6. **Собственная поправка этого раунда.** Предположив по выводу `offset=295` на
   298-строчном файле, что `offset` 0-индексный вопреки документации, я проверил
   гипотезу на файле из 10 нумерованных строк: `offset=3 limit=2` вернул строки
   3 и 4. `offset` 1-индексный, как в описании инструмента; поправка снята до
   публикации. Урок: срез без контрольного файла не доказывает индексацию.
7. **Уточнение методики раунда 14.** Тест через `atime` под `relatime` не
   работает, если `atime` уже новее `mtime`: в этом раунде дважды получен ложный
   «файл не читался». Надёжные признаки — порядок inotify-событий и сравнение
   меток с временем жизни процессов; `atime` годится только после явного сброса
   в прошлое отдельным вызовом.

## write_file: конвейер и привилегии

Последовательность, снятая поллером (все bash-этапы — uid 1001, этап данных —
внутри envd, uid 0):

1. Проба по компонентам пути, **только для путей внутри корня workspace**:

   ```
   [ -e '<parent>' ] && [ ! -d '<parent>' ] && { printf 'FILE:%s\n' '<parent-отн>'; exit 0; }
   [ -d '<target>' ] && { printf 'DIR\n'; exit 0; }
   printf 'OK\n'
   ```

   Для цели под существующим файлом добавляется строка на каждый компонент
   (`FILE:tools/canary15-a.txt`). Для путей вне корня проба не запускается.
2. `mkdir -p '<родитель>'` через обёртку порождения процессов
   (`oom_score_adj=100`, `ionice -c 2 -n 4`, `nice -n 20`). Запускается всегда,
   даже если каталог существует; stderr mkdir попадает в текст ошибки.
3. Загрузка тела через `POST /files` envd от root: создание файла возможно в
   каталоге, куда uid 1001 писать не вправе, затем `chown` к uid 1001
   (inotify: `CREATE` → `ATTRIB` → серия `MODIFY` с шагом ~10 мс).

Измеренные границы:

| Цель | Результат | Комментарий |
| --- | --- | --- |
| `tools/canary15-a.txt` | успех | владелец `user:user 644` |
| `/tmp/outside-workspace-15.txt` | успех | корень workspace не является границей |
| `/etc/…`, `/usr/share/…`, `/opt/…` (755, root) | успех | создание от root c `CAP_DAC_OVERRIDE` |
| `/root/…` (700) | ошибка | `mkdir -p /root/probe15` от uid 1001 → «cannot create directory '/root': Permission denied» |
| `/home/user/AuditArena/../../tmp/x` | ошибка | нормализация `..` лексическая: `mkdir -p /home/tmp` |
| путь, где родитель — файл | ошибка | «Cannot create directory "tools/canary15-a.txt": a file already exists at that path» |
| существующий `root:root 600` в `/opt` | **успех** | владелец стал `user:user`, режим 600 сохранён, содержимое заменено — без sudo |
| существующий `root:root 600` в `/tmp` | ошибка записи | но pre-chown применён: владелец стал `user:user`, и `user` прочитал исходное содержимое |

Последняя строка — самый тонкий результат раунда. Причина отказа не в правах
агента, а в ядре гостя: `fs.protected_regular=2`, `/tmp` sticky и
world-writable, а envd открывает файл с `O_CREAT`. Эксперимент от root:
`O_CREAT|O_TRUNC` на чужой существующий файл в `/tmp` → `EACCES`; тот же файл
без `O_CREAT` (`r+b`) → успех; при `sysctl fs.protected_regular=0` → успех;
возврат в 2 → снова `EACCES` (значение восстановлено). То есть ядро 6.1.158 не
освобождает root от `protected_regular` для чужих файлов в sticky-каталогах, и
envd со своим безусловным `O_CREAT` спотыкается об это. Побочный эффект —
неудачная запись всё равно передаёт владение файлом (pre-chown в `upload.go`
выполняется до открытия).

## read_file: два тракта чтения

1. В VM: `/bin/bash -l -c python3 -I - <<'PY'…` (2832–2963 симв.; параметры
   `path`, `offset`, `limit`, `max_bytes=262144`, `half`; статусы
   `whole/elided/invalid_utf8/open_error`), uid 1001. Оставляет inotify
   `OPEN/ACCESS/CLOSE` и обновляет `atime`.
2. Резервный тракт при `open_error`: `GET /files` envd от root
   (`download.go:138` `os.Open`, `:172` `http.ServeContent`). Доказательство —
   чтение `root:root 600` при `atime`, обновлённом на 53 мс позже завершения
   in-VM python, и невозможность чтения от uid 1001.

Сообщения об ошибках: `File not found: <абс>` (нет файла), `Failed to read
workspace file: <отн>` (каталог или неуспех обоих трактов), `Failed to process
image at <абс>` (произвольный бинарь маршрутизируется в тракт изображений, хотя
описание обещает «metadata only»). Симлинки раскрываются. Пути вне workspace
принимаются. `offset`/`limit` работают с 1-индексацией. PNG возвращается модели
как видимое изображение — мультимодальная петля замкнута (проверено на
сгенерированном файле `images/probe15-blueprint.png`).

## edit_file и present_file

`edit_file` в VM оставляет ровно два процесса (проба + `mkdir -p`); чтение и
запись идут через envd от root (перезапись `root:root 600` в `/opt` удалась; в
`/tmp` отказ по `protected_regular` без изменения содержимого). Сообщения:
`File not found`, `Cannot edit non-text file`, `Failed to read workspace file:
<отн>` для каталога.

`present_file` не трогает VM вообще: в окне четырёх вызовов поллер не увидел ни
одного нового процесса, наблюдатель — ни одного inotify-события по файлам
репозитория. Принимает пути вне workspace и root-файлы `600`; для каталога и
отсутствующего файла сообщение одинаковое: `No file exists at path "<абс>"`.
Чтение выполняется позже, браузером пользователя, через предпросмотр — то есть
через envd от root.

## Серверные инструменты: единый конвейер записи и провайдеры

`image_search` и `generate_image` пишут результат тем же конвейером, что и
`write_file`: проба `[ -d …]`, `mkdir -p`, затем загрузка через envd (inotify
`CREATE` → `ATTRIB` (chown) → `MODIFY` каждые ~10 мс). Процессы загрузки в VM
не появляются.

* `image_search`: провайдер — Brave. Миниатюры приходят с
  `imgs.search.brave.com` (поле `thumbnail_url` в ответе), файлы сохраняются в
  `image-search/<slug>-<n>.<ext>`. Метаданные источника сохраняются: у PNG из
  репозитория firecracker-containerd уцелел чанк `zTXt` с `mxGraphModel`
  (draw.io), у JPEG — EXIF APP1 и прогрессивный SOF2 (imgix).
* `generate_image`: у результата нет ни одного метаданного чанка — только
  `IHDR`, `pHYs`, 68×`IDAT`, `IEND`. Ни tEXt/iTXt, ни EXIF, ни C2PA/XMP:
  происхождение модели по байтам не определяется.
* `web_search`: выдача совпадает с Brave Search API (поле `pageAge`),
  результаты подкрепляют находки прошлых раундов внешними источниками:
  обязательный `X-Access-Token` для прямого доступа к envd
  [1](https://docs.e2b.dev/sandbox/secured-access); «control-plane headers
  (Authorization) намеренно не передаются в data-plane, чтобы учётные данные не
  попадали в гостя» [3](https://deepwiki.com/e2b-dev/E2B/6.3-authentication-and-security);
  «envd runs as root … user code runs as non-root»
  [4](https://agent-sandbox.sigs.k8s.io/docs/use-cases/examples/envd-sandbox/);
  `/init` с токеном на каждый старт VM закрывает окно неаутентифицированного
  envd [6](https://github.com/arugula-salad/wisp/pull/46); схема вывода
  envd-токена через HMAC от секрета сервера в сторонних реализациях
  [2](https://github.com/cocoonstack/sandbox-operator/pull/70),
  [8](https://github.com/gitmoot/sandboxd/issues/21).

## Процессы, зонды и пределы bash/start_process

* Обёртка порождения процессов неизменна с раунда 14: `echo 100 >
  /proc/$$/oom_score_adj && exec ionice -c 2 -n 4 nice -n 20 …`.
* Платформа опрашивает `/tmp/arena-workspace` каждые ~30 с даже в полном простое
  (inotify `OPEN/ACCESS/CLOSE`), независимо от вызовов инструментов.
* Зонд нового порта: через 0,66 с после появления listener, один `GET /` с
  `curl/7.88.1` и заголовками `Accept/Host/User-Agent`.
* `bash` с `timeout=3` против `sleep 8` вернул `status:"timeout"` через 3188 мс
  с частичным stdout и `exit_code:null` — как описано; процесс при этом
  продолжает жить до завершения вызова.
* `get_process_output` с `wait_for:"log"` блокирует до совпадения образца
  (проверено на журнале зонда 8097).
* `sudo -n true` от uid 1001 успешен (группа `sudo`): внутри этой песочницы у
  агента и так есть root, поэтому находки о записи «мимо DAC» ниже — не прирост
  привилегий здесь, а обход документированных границ и потенциальная эскалация
  в шаблонах без sudo.

## Новые риски

**№29. Файловые инструменты работают мимо DAC и вне корня workspace.** Чтение
(резервный тракт `GET /files`) и запись (`POST /files`) выполняются envd от
root: агент без sudo может прочитать любой файл гостя и перезаписать любой
существующий файл, включая `/etc/passwd` и системные бинарники. `/etc/shadow`
намеренно не читался, чтобы не вводить секреты в контекст. Документированное
«rooted at /home/user/AuditArena» — соглашение, а не принуждение.

**№30. Pre-chown до открытия: ошибка записи всё равно передаёт владение.**
Неудачный `write_file` на root-файл в sticky-каталоге оставил файл с владельцем
`user:user` и режимом 600, после чего содержимое стало доступно агенту. Это и
примитив раскрытия, и «осиротевший» побочный эффект при любой ошибке записи.

**№31. `/usr/bin/envd` — root-файл с режимом 777.** Единственный world-writable
root-бинарник в `/usr/bin`, `/usr/sbin`, `/bin`, `/sbin` (проверено `find
-perm -0002 -user root`). Код агента может подменить бинарник демона, который
исполняется от root; действующий процесс не затрагивается, но перезапуск envd
(например при resume) исполнит подменённый код от root. Не проверялось
намеренно.

**№32. `fs.protected_regular=2` ломает перезапись envd в sticky-каталогах.**
Из-за безусловного `O_CREAT` в `upload.go` инструменты не могут обновить
существующий файл в `/tmp`, `/var/tmp`, `/dev/shm` — включая собственные
артефакты платформы в `/tmp/arena-workspace`. Функциональный дефект с
безопасностным оттенком: поведение зависит от sysctl гостя.

**№33. Login-shell при каждом файловом вызове.** `~/.profile` → `~/.bashrc`
(пишутся агентом) исполняются при каждом `read_file`/`write_file`/`edit_file`,
а не только в зонде статуса: точка внедрения кода в каждый вызов инструмента и,
через подмену вывода python-программы, в то, что видит модель. Не
эксплуатировалось.

**№34. Отсутствие метаданных происхождения у сгенерированных изображений.** Ни
C2PA, ни XMP, ни tEXt: файл неотличим по байтам от пользовательского или
стокового. Для аудита это означает, что трассировка происхождения возможна
только по журналам песочницы.

## Что всё ещё не видно отсюда

* Где именно формируется (или не формируется) `warnings`: стартовый зонд
  платформы молчит при 403 и заголовках блокировки; возможно, детектор живёт в
  браузере пользователя при загрузке предпросмотра в iframe.
* TypeScript-сторона файловых инструментов: проба и `mkdir` видны в VM, а
  ветвление «open_error → резервный тракт GET /files» восстановлено по
  косвенным признакам (права, atime, сообщения об ошибках), а не по коду.
* Провайдер `generate_image`: в байтах результата метаданных нет вовсе.
* Полный каталог коннекторов: перечисления нет, только точечные пробы.
* Поведение предпросмотра в браузере пользователя (чтение root-файла через
  `present_file` должно пройти через envd от root) — вне VM не наблюдалось.
