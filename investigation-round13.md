## 2. TLS-перехват: механизм целиком

Раунд 5 зафиксировал сам факт (сертификат `O=E2B, CN=github.com` от `E2B Proxy CA`), раунд 9 — что прокси вшивает `Authorization`, хотя git его не отправляет. Эти два наблюдения не были связаны между собой. Теперь механизм собран целиком.

**Какие хосты перехватываются:**

| Хост | Издатель сертификата | Вывод |
|---|---|---|
| `github.com` | `O = E2B, CN = E2B Proxy CA` | перехват |
| `api.github.com` | `O = E2B, CN = E2B Proxy CA` | перехват |
| `codeload.github.com` | `O = E2B, CN = E2B Proxy CA` | перехват |
| `pypi.org`, `files.pythonhosted.org` | GlobalSign Atlas R3 DV TLS CA 2025 Q4 | подлинный |
| `registry.npmjs.org` | Google Trust Services WE1 | подлинный |
| `objects.githubusercontent.com`, `raw.githubusercontent.com`, `example.com` | соединение не устанавливается | вне allow-list |

Перехватываются ровно те три хоста, для которых платформе нужно добавлять заголовок `Authorization`; для PyPI и npm учётка не вшивается (раунд 10: npm 401, PyPI 303) — и TLS там не трогают.

**Параметры CA и листовых сертификатов:**

- CA: `/usr/local/share/ca-certificates/e2b-ca.crt`, 595 байт, самоподписанный, `CA:TRUE`, ECDSA P-256, `ecdsa-with-SHA256`, срок **14.10.2026 10:14:35 → 14.10.2027 11:14:35**, sha256-отпечаток `68:0F:01:CB:E9:C9:3D:42:5F:67:65:4D:68:79:1D:35:33:25:61:49:BA:A9:9F:96:0F:88:68:67:31:66:0E:85`. **Закрытого ключа в песочнице нет** (0 блоков `PRIVATE KEY`) — гость не может сам выпускать сертификаты от имени этого CA.
- Системный набор: 143 сертификата, ровно один с `E2B` в субъекте; 142 — публичные CA из образа. Каталог `/run/e2b/certs` (285 записей, mtime 15.06.2026 17:00:10) не изменился: перезаписан только файл набора, то есть CA добавлен в доверие без создания хеш-ссылки в каталоге.
- Листовые сертификаты: по одному на хост (серийные `7975A597…`, `DD912342…`, `8F69A61B…`), ECDSA P-256, SAN — одно DNS-имя, срок **25 часов**. Все три выпущены в окне **15:11:27–15:11:31 UTC**, то есть за час до появления этой песочницы, и два соединения подряд отдают один и тот же сертификат ⇒ кэш сертификатов живёт на общем прокси-компоненте, а не внутри песочницы, и переживает отдельные песочницы.

**Как это видит git** (`GIT_CURL_VERBOSE=1 git ls-remote`):

```
Connected to github.com (20.29.134.23) port 443
SSL connection using TLS1.3 / ECDHE_RSA_AES_128_GCM_SHA256
  subject: O=E2B,CN=github.com
  issuer:  O=E2B,CN=E2B Proxy CA
=> Send header: GET /overbaffe1/AuditArena.git/info/refs?service=git-upload-pack HTTP/2
=> Send header: Host: github.com
<= Recv header: HTTP/2 200
```

Подключение идёт к настоящему IP GitHub, значит перехват прозрачный (перенаправление на уровне хоста), а цель выбирается по SNI (раунд 5). Заголовка `Authorization` git не отправляет — его добавляет прокси. Ответы при этом подлинные: `server: github.com` и `x-github-request-id: C1BA:E1FBE:…` присутствуют, то есть прокси дополняет запрос, а не подделывает ответ.

**Обойти перехват нельзя, а закрепить git — нельзя тем более:**

| Проверка | Результат |
|---|---|
| `curl --cacert <набор из 142 публичных CA, без E2B>` | `curl: (60) SSL certificate problem: unable to get local issuer certificate` |
| `curl --cacert <пустой файл>` | `curl: (77) error setting certificate file` |
| `curl` со штатным набором | `200`, `ssl_verify_result=0` |
| `git -c http.sslCAInfo=<набор без E2B> ls-remote` | **код 0 — успех** |
| `GIT_SSL_CAINFO=<набор без E2B> git ls-remote` | **код 0 — успех** |
| `git -c http.sslCAInfo=<пустой файл> ls-remote` | **код 0 — успех** |

git 2.39.5 в этом образе собран против `libcurl-gnutls.so.4` / `libgnutls.so.30`, и GnuTLS игнорирует `http.sslCAInfo`/`GIT_SSL_CAINFO`, беря доверие из системного хранилища. curl те же файлы уважает. Практический смысл: **любое git-действие в песочнице заведомо идёт через прокси платформы, и средствами git это не проверить** — только сторонним инструментом (`openssl s_client`, `curl --cacert`).

## 4. MMDS: границы подтверждены экспериментально

Раунд 12 установил, что дерево метаданных читается любым процессом. В этом ходе проверены свойства защиты:

| Проверка | Результат |
|---|---|
| Токен с `X-aws-ec2-metadata-token-ttl-seconds: 2`, запрос сразу | `200` |
| Тот же токен через 5 с | `401` — **TTL соблюдается** |
| `GET /latest/api/token` вместо `PUT` | `401` |
| Мусорный токен той же длины (48 символов) | `401` — токены проверяются |
| `accessTokenHash` против SHA-512 от пустой строки | **не совпадает** (сравнение выполнено в песочнице, оба значения не печатались) |
| Запись в дерево (`PUT` нового ключа, `DELETE`) | `400` / `501` (раунд 12) |

Последняя проверка закрывает конкретный сценарий из исходника: `checkMMDSHash` трактует `hash("")` в MMDS как «nil-токен разрешён», то есть как санкционированный сброс токена. В этой песочнице хеш не равен SHA-512 от пустой строки, значит сброс не авторизован — что и подтвердилось живой пробой (§5).

## 5. Живая проверка `/init`: предсказание по исходнику сбылось

Сначала прочитал `PostInit` на закреплённом коммите `51ad7ff04f`: тело читается и разбирается, берётся `initLock`, затем вызывается `validateInitAccessToken`, и **только после успеха** устанавливается `defer a.unfreezeUserCgroups(...)` и вызывается `SetData`. Комментарий в источнике прямо объясняет порядок: проверять до разморозки cgroup, чтобы «устаревшие или повторные, но неавторизованные запросы не могли разморозить cgroups».

| Запрос к envd | Предсказание по исходнику | Факт |
|---|---|---|
| `POST /init` с телом `{}` | `ErrAccessTokenResetNotAuthorized` | **`401 access token reset not authorized`** |
| `POST /init` с заведомо ложным 64-hex токеном | `ErrAccessTokenMismatch` | **`401 access token validation failed`** |
| `GET /init` | путь не в `authExcludedPaths` (там указан `POST/init`) | **`401`** с общим текстом про access token |

После проб envd в порядке: `GET /health` → `204`, `GET /` → `401`. Изменений состояния не произошло — ровно как предсказывал исходник.

Выводы:

1. **Процесс внутри песочницы, в том числе root, не может перехватить управление envd через `/init`** — ни сбросить токен, ни подменить свой. Риск №22 раунда 12 остаётся теоретическим: он касается только мгновений до первого `/init`, а не работающей песочницы.
2. Список исключений чувствителен к методу: `POST/init` разрешён без токена, `GET/init` — нет. Совпадает с кодом `slices.Contains(authExcludedPaths, req.Method+req.URL.Path)`.
3. Проверка подписи не даёт оракула: мусорная подпись, просроченная и подпись со сроком в будущем дают одинаковое `401 invalid signature`, а при отсутствии параметра — `401 missing signature query parameter`. По ответу нельзя отличить «неверная подпись» от «истёк срок».
4. `GET /health` → `204` с пустым телом изнутри песочницы; раунд 11 видел снаружи именно пустой ответ, который серверный инструмент принял за ошибку. Совпадение полное.

## 6. Защита токена envd в памяти и граница, которую я не перешёл

- `VmLck: 4 kB` у envd, в `smaps` 31 область с полем `Locked:`, из них одна ненулевая — 4 кБ, то есть одна страница. Это согласуется с memguard из исходника (`Destroy`, `WipeBytes`, `ErrBufferExpired`, `ErrDecryptionFailed`): значение токена держится в запертой памяти и в зашифрованном виде.
- `/proc/1229/mem` имеет права `-rw------- root`, то есть формально root в песочнице может читать память envd.

**Извлекать токен я не стал**, и это осознанная граница, а не техническое ограничение: (а) memguard держит значение зашифрованным, так что дамп памяти не дал бы надёжного результата и превратился бы в разработку эксплойта; (б) добыча живой учётки — уже не аудит; (в) локально это ничего не добавляет: root в песочнице и так владеет всеми файлами и процессами.

Остаточный риск фиксирую как есть: цепочка «root в песочнице → токен envd из памяти → управление песочницей через публично маршрутизируемый порт 49983 (раунд 11)» теоретически возможна. Её стойкость держится на двух вещах: энтропии токена (64 hex-символа от `crypto/rand`, 256 бит) и memguard. Ни то, ни другое я не проверял на прочность.

## 7. Процессы песочницы живут в cgroup, которую envd замораживает

В `/sys/fs/cgroup/user/cgroup.procs` видны PID наблюдателя (1842) и всех моих оболочек этого хода (1843, 1845, 1936, 1951–1954). Из исходника: `unfreezeUserCgroups` вызывается при каждом авторизованном `/init`, а в бинарнике есть строки `freeze %s cgroup` и `unfreeze %s cgroup`. Значит, на паузе пользовательские процессы замораживаются целиком, а при возобновлении размораживаются.

Это механическое объяснение семантики паузы: в связке с режимом паузы `filesystem` (при возобновлении — перезагрузка, по документации E2B) получается картина, которую я наблюдал в раундах 8–12: файлы переживают паузу, процессы — нет, `btime` сдвигается на длительность паузы.

## 9. Риски: обновление списка

**Новый №24 — прозрачный TLS-перехват хостов GitHub с доверенным CA внутри песочницы.** Всё HTTPS-соединение с `github.com`, `api.github.com` и `codeload.github.com` расшифровывается на прокси платформы. Следствия:

- это и есть механизм вшивания учётки, то есть поведение по дизайну;
- любой сторонний код в песочнице (например, скрипт сборки из чужого репозитория), отправляющий секреты на github.com, отдаёт их платформе в открытом виде — как и все прочие данные запросов;
- платформа технически способна изменять и ответы; гость не может это обнаружить, поскольку доверяет CA, а git в этом образе не позволяет закрепить настоящий CA (§2);
- CA действует год и, судя по всему, устанавливается в каждую песочницу; кэш листовых сертификатов общий и переживает песочницы.

Это не дефект, а свойство архитектуры, но его стоит формулировать явно: **доверие к содержимому, полученному из GitHub внутри песочницы, опосредовано платформой**. Для аудита это ещё и эпистемологическая граница: всё, что я узнал через GitHub API в раундах 5–13, прошло через компонент, который я не контролирую и не могу проверить независимо.

**Новый №25 — git в этом образе нельзя закрепить на настоящем CA.** GnuTLS-сборка игнорирует `http.sslCAInfo` и `GIT_SSL_CAINFO` (успех даже с пустым CA-файлом), поэтому стандартный способ убедиться в подлинности сервера для git-операций недоступен. Обнаружить перехват можно только сторонним инструментом.

**Уточнены**: №20 (MMDS — защита строже, чем казалось: TTL, PUT-only, отклонение чужих токенов), №22 (снижен).

**Остаются в силе**: №11 (пустые пароли root/user и sshd), №15 (атрибуция действий агентa пользователю), №16 (наблюдаемость), №18 (снижен в раунде 12), №19 (стадиирование ответов серверных инструментов в Alibaba OSS), №21 (подписные URL как предъявительские способности), №23 (host-check предпросмотра не видит границу).

- Где именно работает перехватывающий прокси (адрес, хост, общий ли он для нескольких песочниц) — из гостя видно только следствие: кэш сертификатов пережил мою песочницу.

- Политика хранения расшифрованного трафика и сроки.
- Как именно платформа обменивает токен `arena-…` из окружения на GitHub-токен: обмен происходит на прокси, в песочнице не виден.
- Порог TTL снимка (между 16,4 мин и 65 мин), состав `POST /logs`, модель и стратегия failover, причина обрыва хода 14.10.
