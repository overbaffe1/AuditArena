## 2. Пауза и возобновление, измеренные изнутри

Наблюдатель фиксирует расхождение `CLOCK_REALTIME` и `CLOCK_MONOTONIC`: во время паузы монотонные часы стоят, а стенные при возобновлении выставляются хостом.

| Момент | Событие | Источник |
|---|---|---|
| 15:11:29,46 | закончился последний tool-вызов прошлого хода | лог наблюдателя |
| 15:12:03,17 | записаны `coding.patch`, `coding.diff`, `coding-numstat.txt` | inotify-подобный снимок (ред. 2) |
| 15:13:59,09 | платформа выполнила в VM скрипт сбора статуса процессов и портов | cmdline потомка envd |
| ≈15:13:59,4 | **пауза**: стенные часы остановились | `real − mono` |
| 15:14:28,63 | **возобновление**: `d_real = 28,927 с` при `d_mono = 0,311 с` → пауза 28,6 с | clock-jump |
| 15:14:28,64 | новый `kworker` (единственный новый процесс до первого tool-вызова) | снимок /proc |
| 15:14:28,672 | перезаписаны `/run/e2b/.E2B_SANDBOX_ID` и `.E2B_TEMPLATE_ID` (идентичный наносекундный штамп) | mtime |
| ≈15:14:30 | перевыпущен токен GitHub: срок `2026-10-16 23:14:30 UTC` | заголовок `github-authentication-token-expiration` |
| 15:14:30 | первый tool-вызов этого хода | — |

Что из этого следует:

- **Суммарное время пауз измеряется изнутри.** Величина `CLOCK_REALTIME − CLOCK_MONOTONIC` («фиктивное время старта») была 14:20:26 при создании песочницы и стала 14:20:55 после возобновления — сдвинулась ровно на длительность паузы. Песочница может сама узнать, сколько времени пользователь отсутствовал, и заметить сам факт паузы. Третий независимый признак — маркер `random: crng reseeded due to virtual machine fork` в журнале.
- **Маркер форка штампуется временем паузы, а не возобновления**: запись в журнале датирована 15:13:59, хотя возобновление случилось в 15:14:28. На момент маркера стенные часы гостя ещё хранят значение, замороженное при паузе, — их выставит хост чуть позже, а chrony сообщит `Forward time jump detected!`. Это ровно та картина, которую раунд 4 описал для 14.10, и поправка раунда 5 подтверждается: pause→resume маркер даёт, создание песочницы из базового шаблона — нет.
- **Перезапись идентификаторов и выпуск токена не порождают процессов в VM.** Между возобновлением (15:14:28,63) и перезаписью `/run/e2b/*` (15:14:28,672) наблюдатель не видел ни одного нового процесса, кроме ядерного `kworker`. Значит файлы пишет уже работающий `envd` (PID 1229) по команде хоста через свой API — без `fork` в госте. Это же объясняет, почему `E2B_TEMPLATE_ID` в окружении инструмента меняется: переменные передаются при каждом вызове, а не читаются из образа.
- **Перед паузой платформа собирает статус** (скрипт §4B) — за 0,3 с до остановки часов. Возобновление ленивое: от него до первого tool-вызова ~1,7 с, и до этого момента в VM не выполняется ничего, кроме ядерных воркеров.

## 3. Конец хода: что именно платформа кладёт в `/tmp/arena-workspace`

| Файл | Размер | Содержимое |
|---|---|---|
| `coding.patch` | 45 838 Б | `diff --git a/investigation-round5.md …`, `new file mode 100644`, `index 0000000..e765b98` |
| `coding.diff` | 45 838 Б | **байт-в-байт то же самое** (md5 `1b3e1394d497049d3d7dd22419a7ac66` у обоих) |
| `coding-numstat.txt` | 30 Б | `280\t0\tinvestigation-round5.md\n` |

Сверка показывает, что это **кумулятивный дифф ветки от её базы, по закоммиченному состоянию**:

- `git diff --numstat 7f14bf3..HEAD` → `280 0 investigation-round5.md` — совпадает с `coding-numstat.txt`;
- `git rev-parse HEAD:investigation-round5.md` → `e765b98…` — совпадает с `index 0000000..e765b98` в патче;
- дифф последнего коммита (`git show --numstat HEAD`) дал бы `16 5` — не совпадает, значит берётся не последний коммит, а вся ветка от базы.

Хронометраж: артефакты записаны через 34 с после последнего tool-вызова — в этом окне модель дописывала итоговый текст хода. Запись однократная: все три файла имеют одинаковый штамп `15:12:03.0253800760` (numstat — `…0293801040`, на 4 мс позже).

Процесса-создателя наблюдатель редакции 2 (опрос `/proc` раз в 0,2 с) не зафиксировал. Две гипотезы: (а) платформа читает файлы через API envd и считает дифф на своей стороне; (б) в VM коротко запускается `git diff`, который живёт меньше периода опроса. Редакция 4 (§6) различает их по счётчику форков в конце **этого** хода: счётчик `/proc/stat:processes` растёт на каждый `fork` в системе, поэтому пропуск невозможен в принципе.

Практический смысл для пользователя: вкладка Diff, аварийный `/download-workspace` и эти артефакты описывают одно и то же — состояние ветки относительно её базы, накопительным итогом. Незакоммиченные изменения рабочей папки в патч не попадают (проверено по совпадению blob-хеша с `HEAD`).

## 4. Как платформа опрашивает процессы и порты (полные тексты — приложение Б)

Наблюдатель снял оба служебных скрипта, которые хост запускает в VM через envd как обычные `bash -l -c`.

**Скрипт A — статус одного процесса** (`get_process_output`, а также опросы во время `startup_wait`): печатает `===ARENA_STATUS===` (по `meta.json` / `exit` / `pid` + `kill -0`), затем `===ARENA_LOG===` — `tail -c 80000 out.log | tail -n N`, где `N` подставляется из параметра tool-вызова (в этом ходе наблюдались `N=120` и `N=5`), затем `===ARENA_PORTS===` — `ss -ltnH`. Во время `startup_wait=6` скрипт выполняется примерно раз в 0,5 с (7 запусков за 5 секунд).

**Скрипт B — опрос всех зарегистрированных процессов**: обходит `/tmp/arena-workspace/procs/*/`, для каждой записи печатает `===ARENA_ENTRY===`, `meta.json`, статус (`exited <код>` / `running <pid>`), и если процесс жив — `===ARENA_PORTS===` с фильтром: берётся `ps -eo pid=,pgid=` и `ss -ltnpH`, затем awk отбирает слушающие сокеты, чей PID входит в группу процесса. Так вычисляются `listening_ports` и `new_ports` в результатах `start_process`. Запускается и сам по себе, примерно раз в 2,5–3 минуты, пока в реестре есть записи (наблюдалось в 15:13:59, 15:38:36, 15:41:12).

Наблюдения, которые из этого следуют:

- Часть логики платформы исполняется **внутри песочницы** как обычный shell-скрипт от имени `user`, а не только на хосте. Параметры tool-вызова интерполируются в текст скрипта: пути — в одинарных кавычках, числовые значения (`tail -n N`) — без кавычек. Идентификатор процесса генерирует платформа, а не пользователь, поэтому практически это не вектор, но сам факт стоит знать при оценке границ.
- **Фоновые процессы** (`start_process`) запускаются обёрткой `bash -c 'bash -l "$0/run.cmd" > "$0/out.log" 2>&1; echo $? > "$0/exit"' <каталог>` и выносятся в **отдельную сессию и группу**: `ppid=1`, `pgid=sid=pid` обёртки. В `procs/<id>/pid` записан PID обёртки, а не полезной нагрузки. Именно поэтому `stop_process` может убить всё дерево одним SIGTERM по группе.
- **Обычные tool-вызовы** — дети `envd` и живут в группе и сессии самого envd (`pgid=sid=1229`), то есть не отделяются.
- Записи в `procs/` не удаляются после остановки процесса; при `stop_process` файл `exit` не появляется (обёртка убивается вместе с группой и не успевает его записать). За этот ход в реестре накопилось 4 записи от трёх редакций наблюдателя и одного неудачного запуска.

## 5. Чем в этом образе можно наблюдать, а чем нельзя

Попытка получить точные записи о процессах (без слепых зон опроса) уперлась в сборку ядра:

| Механизм | Состояние |
|---|---|
| ftrace / tracefs | `# CONFIG_FTRACE is not set` → `/sys/kernel/debug/tracing` не существует, смонтировать tracefs некуда |
| netlink `PROC_CONNECTOR` | `CONFIG_CONNECTOR=y`, `CONFIG_PROC_EVENTS=y`, слушатель регистрируется без ошибки, но **ни одной датаграммы не приходит** (проверено от root, четыре варианта `bind`: `(0,0)`, `(0,1)`, `(pid,1)`, `(pid,0)`); единственный сокет протокола 11 в VM — ядерный (portid 0, без процесса-владельца) |
| `/proc/stat:processes` | работает: счётчик растёт на каждый `fork` → даёт **доказуемую** полноту по факту создания процессов |
| `/proc/<pid>/task/<tid>/children` | работает (`CONFIG_PROC_CHILDREN=y`) |
| inotify | работает, включая автоматическое добавление watches на новые подкаталоги |
| journald | работает, журнал непрерывен с сборки шаблона |
| audit | `CONFIG_AUDIT=y`, systemd и journald держат netlink-сокеты AUDIT, но `_TRANSPORT=audit` пуст: правил нет, записей не возникает |

Профиль усиления ядра в образе (читается из `/proc/sys`):

`fs.protected_regular=2`, `fs.protected_fifos=1`, `fs.protected_symlinks=1`, `fs.protected_hardlinks=1`, `fs.suid_dumpable=0`, `kernel.randomize_va_space=2`, `kernel.unprivileged_bpf_disabled=2`, `kernel.perf_event_paranoid=2`, `vm.unprivileged_userfaultfd=0` — при этом `kernel.dmesg_restrict=0`, `kernel.kptr_restrict=0`, Yama отсутствует (`ptrace` без ограничений), SELinux в ядре есть, но `enforce=0`. Suid-бинарников 12 (стандартный набор Debian плюс `fusermount3`, `ssh-keysign`, `mount.nfs`).

Побочное открытие, которое объяснило странность при запуске наблюдателя: `fs.protected_regular=2` запрещает открывать с `O_CREAT` чужой обычный файл в sticky-каталоге с мировой записью (например, в `/tmp`), **и это не обходится capability**. Root с полным `CapEff=000001ffffffffff` получил `EACCES` на дозапись своего же лога, созданного от `user`, зато свободно писал в `/home/user` (не sticky) и создавал новые файлы в `/tmp`. Пришлось передать лог root'у (`chown root:user`, `chmod 664`). Для аудита это полезная граница: процесс в песочнице не может подменить чужие файлы в `/tmp`, даже если он root.

## 6. Следы действий агента внутри VM

- `sudo`: каждая команда вместе с текстом (`sudo[…]: COMMAND=…`) — за сессию больше ста записей.
- PAM/sshd: проверки входа из раунда 5 остались в журнале дословно — `pam_unix(sshd:auth): user [user] has blank password; authenticated without it` (15:00:45) и то же для `root` (15:00:46). Это независимое подтверждение находки раунда 5 §5 прямо из журнала образа: пустой пароль не «угадан», а принят как пустой.
- `audit`: записей нет (§5).
- Текста чата в VM нет (проверено в раунде 5, методика та же); выводы инструментов не сохраняются, кроме моих собственных перенаправлений.

Итог по этому пункту не изменился: внутри песочницы осаждается то, что агент **выполнил** (sudo, входы, собственные файлы), но не то, что ему **сказали**.

## Приложение Б. Полные тексты служебных скриптов платформы

**Б.1. Скрипт A — статус одного процесса** (запускается хостом через envd при `get_process_output` и при опросах во время `startup_wait`; `<dir>` = `/tmp/arena-workspace/procs/<processId>`, `N` подставляется из параметра tool-вызова):

```sh
echo '===ARENA_STATUS==='
if [ ! -f '<dir>/meta.json' ]; then echo "not_found"
elif [ -f '<dir>/exit' ]; then echo "exited $(cat '<dir>/exit' 2>/dev/null)"
elif pid=$(cat '<dir>/pid' 2>/dev/null) && [ -n "$pid" ] && kill -0 "$pid" 2>/dev/null; then echo "running $pid"
else echo "exited"
fi
echo '===ARENA_LOG==='
tail -c 80000 '<dir>/out.log' 2>/dev/null | tail -n N || true
echo '===ARENA_PORTS==='
(command -v ss >/dev/null 2>&1 && ss -ltnH) || netstat -ltn 2>/dev/null || true
```

**Б.2. Скрипт B — опрос всех зарегистрированных процессов и их портов**:

```sh
[ -d '/tmp/arena-workspace/procs' ] || exit 0
ports_observed=
if command -v ss >/dev/null 2>&1; then
  sockets=$(ss -ltnpH) || exit 1
  ports_observed=1
elif command -v netstat >/dev/null 2>&1; then
  sockets=$(netstat -ltnp) || exit 1
  ports_observed=1
fi
if [ -n "$ports_observed" ]; then groups=$(ps -eo pid=,pgid=) || exit 1; fi
for dir in '/tmp/arena-workspace/procs'/*/; do
  [ -f "$dir/meta.json" ] || continue
  echo '===ARENA_ENTRY==='
  cat "$dir/meta.json"
  echo
  if [ -f "$dir/exit" ]; then echo "STATUS exited $(cat "$dir/exit" 2>/dev/null)"
  elif pid=$(cat "$dir/pid" 2>/dev/null) && [ -n "$pid" ] && kill -0 "$pid" 2>/dev/null; then
    echo "STATUS running $pid"
    if [ -n "$ports_observed" ]; then
      echo '===ARENA_PORTS==='
      printf '%s\n' "$groups" "$sockets" | awk -v group="$pid" '
        NF == 2 { if ($2 == group) members[$1] = 1; next }
        $1 ~ /^tcp/ && $7 ~ /^[0-9]+\/[0-9]+/ { if (($7 + 0) in members) print; next }
        { n = split($0, parts, "pid="); for (i = 2; i <= n; i++) if ((parts[i] + 0) in members) { print; break } }
      '
    fi
  else echo "STATUS exited"
  fi
done
```
