# Раунд 9: как платформа собирает патчсет — механизм целиком, и где на самом деле живёт учётка GitHub

Проверка 16.10.2026, 21:08–21:35 UTC. Песочница **та же** (`ici6bh8ik7dr9i6yzrmw5`) — возобновление после паузы 16 мин 25 с. Продолжение `investigation-round8.md`.

Границы прежние: только своя VM, чтение + `sudo`; значения токенов не выводятся (только тип, префикс, длина); чужие песочницы, репозитории и ветки не трогаются; в `main` не пушим; силовой пуш не применялся. Все зонды раунда 8 удалены, фоновый процесс остановлен (§8).

Главный результат: снят **полный механизм сборки патчсета** — платформа запускает git внутри песочницы, в отдельном индексе, и этот патч потом восстанавливает рабочую папку в новой песочнице. Гипотеза проверена применением патча к базовому коммиту (§4). Дополнительно выяснено, что настоящей учётки GitHub в песочнице нет вовсе: её подставляет прокси (§5).

## 2. Скрипт-сборщик: git внутри песочницы, в отдельном индексе

Наблюдатель снял командную строку целиком (текст — в приложении Б). Суть:

```
BASE=<SHA базы сессии>                     # 7f14bf3bdf52550633ee6ca4531de5ef3b05bfd5
export GIT_INDEX_FILE=/tmp/arena-workspace/coding.index      # ОТДЕЛЬНЫЙ индекс
trap 'rm -f "$CODING_INDEX" "$CODING_INDEX.lock" "$CODING_EXCLUDE"' EXIT
printf '%s\n' <30 шаблонов> > /tmp/arena-workspace/coding-exclude
git -c core.excludesFile="$CODING_EXCLUDE" read-tree HEAD     # индекс = HEAD
git -c core.excludesFile="$CODING_EXCLUDE" add -A             # индекс = рабочее дерево
git diff --cached --binary "$BASE" -- . <31 pathspec-исключение> > coding.patch
git diff --cached          "$BASE" -- . <31 pathspec-исключение> > coding.diff
git diff --cached --numstat "$BASE" -- . <31 pathspec-исключение> > coding-numstat.txt
```

Что это даёт:

- **Ответ на вопрос раунда 6**: патчсет считается **внутри песочницы**, обычным git'ом, от базы сессии, по состоянию рабочего дерева. Ни хостового сканирования, ни tar-архива: в окне сборки наблюдатель видел только `bash`, `git` и их детей; всплеск чтений (64 различных пути, 98 открытий) — это git читал `.git/HEAD`, `config`, `packed-refs`, `refs`, файлы рабочей папки.
- **Моя настоящая `.git/index` не затрагивается** — платформа работает в собственном индексе через `GIT_INDEX_FILE`. Состояние git агента (индекс, stash, незакоммиченные намерения) не искажается служебной операцией. Отмечаю как аккуратное решение.
- `read-tree HEAD` + `add -A` = «взять HEAD, наложить рабочее дерево»: в дифф против базы попадают и изменения отслеживаемых файлов, и новые файлы, и удаления.
- `--binary` есть только у `coding.patch`, поэтому `coding.patch` (638 754 Б) больше `coding.diff` (554 212 Б) на 84 542 Б — это base85-блок моего 64-килобайтного двоичного зонда (`GIT binary patch`, ровно один в файле). В `coding.diff` тот же файл представлен строкой `Binary files /dev/null and b/probe-r8-binary.bin differ`. **Поправка к раунду 6**: `coding.patch` ≡ `coding.diff` только пока двоичных изменений нет; это две разные команды.
- `trap … EXIT` убирает служебные индекс и список исключений, но оставляет три артефакта — поэтому после возобновления их можно прочитать (чем я и воспользовался).
- Индекс получился на **19 записей** (заголовок `DIRC` версия 2, `0x13`, 1726 Б): 3 файла базового коммита + 16 добавленных патчем. Сходится с проверкой в §4.

## 5. Учётные данные GitHub: в песочнице их нет, их подставляет прокси

| Проверка | Результат |
|---|---|
| `GH_TOKEN` и `GITHUB_TOKEN` | одинаковые, **24 символа, префикс `arena-`** — не похож ни на `ghs_`, ни на `ghp_`, ни на `github_pat_` |
| `GIT_TERMINAL_PROMPT` | `0` (запрос учётных данных запрещён) |
| `/etc/gitconfig`, `~/.gitconfig`, `~/.git-credentials` | отсутствуют |
| `credential.helper`, `url.*.insteadOf` | не заданы |
| Заголовки `git push --dry-run` (GIT_CURL_VERBOSE) | отправлено 6 заголовков: `GET`, `Host`, `user-agent`, `accept`, `accept-encoding`, `pragma`; **`Authorization` — 0 раз** |
| `GET https://api.github.com/user` со штатной заглушкой (`Bearer`) | 200, `login=overbaffe1`, `id=122226143` |
| то же с заведомо неверным токеном | **200**, тот же пользователь |
| то же **без заголовка авторизации вообще** | **200**, тот же пользователь |
| то же со схемой `token <заглушка>` | 200 |
| Контроль: `https://example.com/` | `SSL_ERROR_SYSCALL` — egress только через прокси (раунд 5) |

Вывод: **прокси безусловно подставляет настоящую учётку и не смотрит на то, что прислала песочница**; заглушка в `GH_TOKEN` нужна лишь затем, чтобы инструменты вроде `gh` не отказывались работать. git аутентифицируется тем же путём — поэтому push проходит при полном отсутствии учётных данных в настройках.

Два следствия, противоположных по знаку:

- **Положительное.** Вынести из песочницы нечего: 24-символьная заглушка работает только через egress-путь этой песочницы. Это же объясняет, зачем патчсет исключает `.git/config`, `.git/credentials`, `.git-credentials`, `.netrc` — защита на случай, если настоящая учётка когда-нибудь окажется в файле. Проверил: ни в `coding.patch`, ни в `coding.diff`, ни в `coding-numstat.txt` значения токена из окружения нет (сравнивал с значением, не выводя его); вхождения строки `ghs_` в логе наблюдателя — это текст моих же команд, попавший в лог (§7).
- **Отрицательное.** Учётка становится **фоновой (ambient) для любого кода в песочнице**. Любой процесс — включая зависимости, которые allow-list как раз разрешает ставить с `registry.npmjs.org` и `pypi.org` — может выполнить `curl https://api.github.com/…` и получить полномочия установки GitHub App от имени пользователя: по данным раунда 5 это `permissions.admin=true` на репозитории и **отсутствие защиты ветки `main`**. Различить «инструмент агента» и «произвольный код агента» прокси не может, поскольку сами инструменты выполняются внутри песочницы.

## 6. Что платформа делает сразу после сборки: ищет последний пуш по локальному reflog

Через 1,3 с после артефактов выполнен скрипт (полный текст, 344 символа):

```
set -o pipefail
git rev-parse --verify -q 'refs/remotes/origin/arena/404c5158-auditarena' >/dev/null
code=$?
[ "$code" -eq 1 ] && exit 0
[ "$code" -ne 0 ] && exit "$code"
git reflog show --format='%H%x09%gs' 'refs/remotes/origin/arena/404c5158-auditarena' \
  | awk -F '\t' '!found && $2 == "update by push" { print $1; found = 1 }'
```

Платформа определяет, какой коммит агент запушил, по **локальному reflog** remote-tracking ссылки. Следствие, связанное с раундом 7 §2: после пересоздания песочницы клон не создаёт `refs/remotes/origin/<ветка>` (в `packed-refs` только `origin/main`), reflog пуст, `rev-parse --verify` возвращает 1 — и скрипт молча выходит с кодом 0. То есть **в свежей песочнице платформа не видит пушей предыдущих ходов**, пока агент сам не выполнит `git fetch`. Это согласуется с тем, что откат ветки к базе сессии не исправляется автоматически: платформа просто не знает, что вершина уехала вперёд.

## 7. Метрологические поправки к инструменту

- **Метки времени в логе отстают от событий.** mtime артефактов: 07,082 / 07,090 / 07,098 (интервалы 8 мс); метки тех же событий в логе: 07,166 / 07,190 / 07,203 — отставание 84–105 мс. Причина: на каждом событии наблюдатель считает md5 файлов по 0,5–0,6 МБ и пишет строку в два файла. Порядок событий достоверен, абсолютное время — нет; дальше опираюсь на mtime.
- **Детектор `GIT_OR_TAR_IN_VM` не сработал ни разу, хотя git запускался**: условие разбивало командную строку по `/`, а у `git -c core.excludesFile=/tmp/…` последний сегмент — не имя программы. Команды всё равно сняты целиком записями `cmdline_new`. В копии скрипта, которая остаётся в репозитории, детектор исправлен на `os.path.basename(cmd.split(' ')[0])`, а лимит командной строки поднят с 2500 до 8000 символов (в этом ходе хвост скрипта-сборщика срезался на 2500).
- **Самоцитирование**: лог наблюдателя лежит в рабочей папке, содержит командные строки моих же tool-вызовов и сам попадает в патчсет; анализ лога увеличивает лог. Это надо учитывать и при проверках на утечки (grep по логу находит мои же литералы), и при оценке размера патчсета.

## 8. Поправки к прошлым отчётам

- Раунд 8 §2: граница TTL снимка — 16,4 мин ещё возобновляется; интервал сузился до 16,4–63 мин.
- Раунд 8 §3: `btime` переустанавливается и при возобновлении, не только при пересоздании (§1).
- Раунд 8 §9, риск 9 (symlink): **закрыт** — ссылки переносятся как ссылки, mode 120000 (§3).
- Раунд 8 §9, риск 8 (черновики): подтверждён напрямую через numstat (§3).
- Раунд 8 §1: формула переноса уточнена до механизма — рабочая папка восстанавливается применением `coding.patch` к базовому коммиту (§4); отсюда же следует, что глобальный игнор не защищает, а локальные правила игнора действуют.
- Раунд 6: `coding.patch` ≡ `coding.diff` лишь при отсутствии двоичных изменений (§2).
- Раунд 6 §3 (вопрос «VM или хост»): закрыт — сборка идёт в VM (§2).
- Раунд 5 §6: «заглушка `arena-` не нужна» — уточняется: заглушка присутствует в `GH_TOKEN`/`GITHUB_TOKEN` (24 символа), но прокси аутентифицирует независимо от её значения (§5).
- Раунд 7 §2: механизм отката ветки дополнен причиной — платформа судит о пушах по локальному reflog, которого в новой песочнице нет (§6).

## 9. Риски: дополнения к спискам раундов 5, 7, 8

11. **Фоновая учётка GitHub для любого кода в песочнице** (§5) — самый значимый риск всего аудита. Что делать владельцу репозитория: включить защиту `main` и ограничить установку GitHub App нужными репозиториями. Что делать платформе: либо брокер учётных данных вне песочницы, где аутентифицируются только вызовы инструментов агента, либо краткосрочный токен с областью «только эта ветка этого репозитория». Сейчас `permissions.admin=true`, защиты `main` нет, а allow-list разрешает именно те хосты, которые нужны для обращения к API.
12. **Глобальный игнор не защищает от патчсета** (§3): файлы, исключённые через `~/.config/git/ignore`, всё равно в него попадают. Агенту следует использовать `.gitignore` репозитория или `.git/info/exclude`.
13. **Патчсет переносит неотслеживаемые файлы целиком, включая двоичные** (§3): случайный дамп или артефакт сборки уедет в артефакты сессии, если не попадает в список исключений платформы. Ограничение 128 МБ / 10 000 файлов из системных указаний при этом не проверялось.
14. **Платформа не видит пушей прошлых ходов после пересоздания песочницы** (§6): возможно расхождение между тем, что знает агент, и тем, что знает платформа о состоянии ветки.
