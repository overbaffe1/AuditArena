## 3. Где исполняются инструменты: канареечный эксперимент

Метод. В корне репозитория создан файл `canary.db-wal` (имя намеренно попадает под исключение сборщика `**/*.db-wal`, чтобы не загрязнять патчсет). Его `atime` сбрасывался в 2020-01-01: корень смонтирован с `relatime`, поэтому следующее чтение обязано обновить `atime`. Параллельно наблюдатель считал события inotify `OPEN`/`ACCESS`/`CLOSE` по пятисекундным окнам. Контроль — локальный `cat`: `atime` обновился ✓.

Первая попытка оказалась испорчена, и это стоит зафиксировать как ошибку метода: `atime` обновил мой же `git status` в том же вызове, а после этого `relatime` не обновляет `atime` сутки, поэтому последующее серверное чтение стало невидимым. Переделано: сброс `atime` — отдельным вызовом, без других обращений к файлу.

**Поправка к модели, которую я использовал в раундах 3–13** (по документации Arena: «серверные инструменты работают вне песочницы»). Вне песочницы работают сетевые инструменты. **Файловые инструменты читают и пишут на живой файловой системе песочницы**, порождая процессы — дети envd. Для `read_file` это доказано двумя независимыми сигналами и полным текстом программы; для `edit_file` — метками времени файла и счётчиком вилок.

Отдельно: как `present_file` доставляет содержимое в просмотрщик пользователя, из песочницы не видно — в момент вызова файл не читается, а наблюдатель не доживает до момента, когда пользователь реально откроет файл.

## 4. Реализация `read_file` (полный текст в Приложении Б)

Что видно из снятой программы (2846 символов):

- Параметры вшиваются в код литералами: `path`, `offset`, `limit`, `max_bytes = 262144`, `half = max_bytes // 2`.
- Запуск — `python3 -I -` с программой через heredoc. Ключ `-I` игнорирует переменные `PYTHON*` и пользовательский site-packages, а подача программы через stdin закрывает перехват через `PYTHONSTARTUP`. Проверено: `sys.path` при `-I` — `/usr/lib/python311.zip`, `/usr/lib/python3.11`, `lib-dynload`, `/usr/local/lib/python3.11/dist-packages`, `/usr/lib/python3/dist-packages`.
- Чтение кусками по 1 МиБ, снятие UTF-8 BOM, строгая проверка кодировки: при ошибке — статус `invalid_utf8`; не-обычный файл или отказ открытия — `open_error`.
- Считаются размер и число строк всего файла, выбирается диапазон строк; ответ — JSON в stdout: `{"status":"whole","size":…,"lines":…,"text":<base64>}` либо `{"status":"elided",…,"head":<base64 128 КиБ>,"tail":<base64 128 КиБ>}`. Содержимое передаётся **в base64**, то есть через тот же канал проходят и бинарные файлы.
- То, что вижу я (`kind`, `lines`, `size`, `content`), — уже декодированный ответ: base64 разбирается на стороне платформы.

Практический смысл: `read_file` — обычная программа, выполняемая в песочнице, и её вывод формируется там же. Собственной защиты от подмены у неё нет (§5).

## 5. Вектор подмены вывода инструментов: world-writable `dist-packages`

- `/usr/local/lib/python3.11/dist-packages` имеет права **`drwxrwxrwx root:root`** — запись доступна любому пользователю, включая непривилегированного `user` (uid 1001), под которым работают инструменты платформы.
- `sitecustomize.py` в этом каталоге **не сработал**: имя уже занято штатным файлом — `/usr/lib/python3.11/sitecustomize.py` → `/etc/python3.11/sitecustomize.py` (принадлежит root), и он раньше в `sys.path`. Мой маркерный файл не выполнился, что я и наблюдал.
- **`.pth`-файл сработал.** Созданный от `user` файл `zzz-audit-probe.pth` (47 байт, права 644) с единственной строкой `import sys; sys.stderr.write("PTH-EXECUTED\n")` выполнился при старте интерпретатора:
  - `python3 -I -c pass` → маркер напечатан;
  - `python3 -I -` с heredoc (ровно так запускается `read_file`) → маркер напечатан **до тела программы**;
  - `python3` без `-I` → маркер напечатан.
  Ключ `-I` не отключает обработку `.pth` — её отключает только `-S`.
- Чистота подтверждена тремя способами: листинг каталога (пуст), `find / -xdev -name '*.pth' -newermt '2026-10-17 17:00'` (ничего), повторный `python3 -I -c pass` (маркера нет). Время существования файла — доли секунды внутри одного вызова.

**Следствие (новый риск №27).** Любой код, запущенный в песочнице от обычного пользователя, — скрипт сборки чужого репозитория, тесты, хук установки пакета — может положить `.pth`-файл, который выполнится **внутри каждого последующего запуска Python**, включая процессы файловых инструментов платформы. Это даёт возможность подменять то, что видит модель: содержимое файлов, возвращаемое `read_file`, и, предположительно, результат записи `write_file`/`edit_file`. Для Arena это прямой путь к последствию «Deceptive Completion» из Alignment Index, но инициированный не моделью, а скомпрометированной песочницей: модель добросовестно сообщит о результате, который ей подменили.

Ни root, ни занятия имени не требуется. Для сравнения: правка самого stdlib (`/usr/lib/python3.11/base64.py`, `json/__init__.py` — принадлежат root) дала бы тот же эффект, но требует root, а root в этой песочнице получается без пароля (раунд 5, риск №11) — то есть оба пути открыты, один из них вообще без привилегий.

## 6. Мелочи и подтверждения

- **Каждый вызов `bash` — login-shell**: в окнах наблюдателя на каждый вызов видны `OPEN`/`ACCESS`/`CLOSE` для `~/.bashrc` (трижды) и `~/.profile` (дважды). Эти файлы принадлежат `user` и читаются при каждом вызове инструмента — та же точка влияния, что и `.pth`, но для bash (риск №28).
- Платформа проверяет живость фонового процесса **чтением файла** `procs/<id>/pid`: девять `OPEN`/`ACCESS`/`CLOSE` за первое окно наблюдения — по числу зондов, снятых поллером.
- **Зонд состояния платформы снят целиком (862 символа).** Обёртка: `/bin/sh -c echo 100 > /proc/$$/oom_score_adj && exec /usr/bin/ionice -c 2 -n 4 /usr/bin/nice -n 20 "${@}" -- /bin/bash -l -c`, тело — три раздела с маркерами:
  - `===ARENA_STATUS===` — проверка `meta.json`, затем `exit` (ответ `exited <код>`), затем `pid` + `kill -0` (ответ `running <pid>`), иначе `not_found`/`exited`;
  - `===ARENA_LOG===` — `tail -c 80000 out.log | tail -n 120`;
  - `===ARENA_PORTS===` — `ss -ltnH` (или `netstat -ltn`).
  За 4,6 с после `start_process` зонд выполнился девять раз (интервал ~580 мс).

  Отсюда три уточнения к прошлым раундам. Поля `listening_ports`/`new_ports` в ответах `start_process` — это вывод `ss -ltnH` внутри песочницы (только слушающие TCP). Журнал фонового процесса покидает песочницу порциями до 80 КБ и 120 строк — конкретизация наблюдения раунда 9 («stdout покидает VM»). Статус процесса определяется по файлу `exit`, который пишет обёртка запуска: поправка к раунду 11 («признака завершения нет») закрыта текстом самой платформы — файл есть, но появляется только при естественном завершении.

  И главное: зонд — **login-shell**, поэтому он читает `~/.profile`, а тот на строках 13–15 подключает `~/.bashrc`. Оба файла принадлежат `user` и доступны ему на запись. В окне наблюдателя 17:28:28.256, где из посторонней активности были только три зонда, зафиксированы `OPEN`/`ACCESS`/`CLOSE` для `.bashrc` и `.profile`, тогда как в окнах без зондов (17:28:33, 17:28:58, 17:29:28) их нет ⇒ **код из `~/.bashrc` исполняется внутри периодического зонда платформы**, без единого вызова инструментов агентом.
- Счётчик вилок за ход: 1683 → 1695; `/proc/stat:processes` = 1704. Правка `edit_file` дала три вилки за 135 мс (1684 → 1687).
- git-состояние: после `fetch` и `reset --mixed` расхождений с remote 0, неотслеживаемых файлов 0 — **третье** подтверждение того, что накопительный патч восстанавливает рабочее дерево байт-в-байт.
- `.sudo_as_admin_successful` на момент 17:11:5x отсутствовал (бутстрап закончился в 17:11:07) — третье подтверждение поправки раунда 13: маркер создаёт первый `sudo` агента, а не платформа при старте.
- Журнал наблюдателя в этом ходе намеренно пишется и в репозиторий (`ARENA_WATCH_REPO_LOG=1`): урок раундов 12–13 в том, что журнал в `/tmp` переживает только возобновление, а при пересоздании данные конца хода теряются. Плата — самоцитирование журнала в патчсете (раунды 9–11).

## 7. Предел метода и новый инструмент

Наблюдатель с периодом опроса 10 мс снял `read_file` (процесс живёт порядка 300 мс), но пропустил процессы `edit_file` (три вилки за 135 мс). Это предел метода: опрос всей таблицы процессов не успевает за короткоживущими детьми.

Добавлен `tools/envd-children-poller.py`: опрос `/proc/<envd>/task/*/children` с периодом 1 мс, снятие `cmdline` у каждого нового PID и контроль полноты по счётчику `/proc/stat:processes` — если счётчик вырос, а нового ребёнка не появилось, процесс родился и умер между опросами, и такой пропуск учитывается. Поскольку все инструменты платформы — прямые дети envd (раунд 12), выборка получается полной без перебора всей таблицы процессов. Расчёт на следующий раунд: снять реализации `write_file` и `edit_file`.

Первые же записи поллера дали результат, которого я не планировал, — **обёртку, через которую envd порождает любой процесс**. В журнале снят `/bin/sh -c` с текстом `/bin/sh -c echo 100 > /proc/$$/oom_score_adj && exec /usr/bin/ionice -c 2 -n 4 /usr/bin/nice -n…` (862 символа вместе с аргументами команды) — в точности та строка формата, которая нашлась в бинарнике envd в раунде 13. Смысл обёртки: `oom_score_adj = 100` повышает вероятность того, что при нехватке памяти убьют именно этот процесс (сам envd имеет `OOMScoreAdjust=-1000`, раунд 5), а `ionice -c 2 -n 4` вместе с `nice` понижает его приоритет по вводу-выводу и по процессору. То есть **процессы агента сделаны жертвенными по отношению к управляющему процессу песочницы**: при нехватке памяти или перегрузке первым пострадает код агента, а не envd. Это сознательная изоляция, а не побочный эффект, и она объясняет, почему управляющий канал выживает при убийстве рабочих процессов.

## 8. Поправки к прошлым отчётам

1. **Модель «серверные инструменты работают вне песочницы»** (раунды 3–13, по документации Arena) — уточнена: вне песочницы работают сетевые инструменты; файловые исполняются внутри песочницы процессами-детьми envd (§3).
2. **Раунд 9**: «прокси вшивает `Authorization` безусловно» — показано прямым экспериментом: перезаписывается даже явно заданный агентом заголовок (§2).
3. **Раунд 13 §1**: файлы сертификатов и идентификаторов приходят с хоста пачками с идентичными наносекундными метками; интерпретация «пересборка набора сертификатов в песочнице» заменена на «пакетная запись через API envd» (§1).
4. **Раунды 8, 10, 12**: ряд порогов TTL дополнен значением ~49 мин; граница между возобновлением и пересозданием — от 16,4 мин до 49 мин (§1).
5. **Раунд 12 §1 / раунд 13 §8**: маркер `.sudo_as_admin_successful` — третье независимое подтверждение (§6).
6. **Раунд 11 §2, вывод 3** (traffic-токена в песочнице нет) остаётся в силе и не противоречит §2 этого раунда: речь о разных токенах — граничный токен предпросмотра в гостя не передаётся, а GitHub-учётка и не нужна, её подставляет прокси.

## 9. Риски: обновление списка

**Новый №26 — код в песочнице действует в GitHub как пользователь, не имея учётных данных.** В сочетании с правами установки `contents:write`, `pull_requests:write` и **`workflows:write`** (раунд 10) и с получением root без пароля (раунд 5) это даёт стороннему скрипту сборки путь к исполнению кода **вне песочницы**: запушить файл workflow и получить запуск на раннерах GitHub Actions. Не проверял — это было бы записывающим действием в репозитории пользователя.

**Новый №27 — подмена вывода файловых инструментов через world-writable `dist-packages` и `.pth`** (§5). Не требует привилегий, срабатывает до тела программы инструмента, влияет на то, что видит модель.

**Новый №28 — `~/.bashrc` исполняется периодическим зондом платформы, а вывод зонда разбирается по маркерам** (§6). Зонд — login-shell, поэтому читает `~/.profile` → `~/.bashrc`; оба файла принадлежат `user` и доступны на запись любому коду в песочнице. Следствие шире, чем у №27: такой код выполняется **даже когда агент не делает вызовов** (зонд идёт с интервалом ~0,6 с после запуска фонового процесса и периодически дальше), а его stdout платформа разбирает по маркерам `===ARENA_STATUS===`, `===ARENA_LOG===`, `===ARENA_PORTS===`. Значит, скомпрометированная песочница может подделывать ответ зонда: сообщать о несуществующих слушающих портах, скрывать реальные, подменять статус процесса (`running`/`exited`) и вставлять произвольный текст в «журнал», который видят и агент, и пользователь. Это же объясняет ненадёжность механизма `warnings` (риск №23): он опирается на данные, собранные внутри среды, которой управляет проверяемый. Подмену я не выполнял — возможность установлена по тексту зонда и по событиям чтения `.bashrc`.

**Уточнены**: №11 (пустые пароли) — теперь ещё и ступень к №27 через правку stdlib; №15/№16 — без изменений.

**Остаются в силе**: №18 (снижен), №19, №20, №21, №22 (снижен), №23, №24, №25.

## 10. Что всё ещё не видно отсюда

- Полный текст реализаций `write_file`, `edit_file` и поведение `present_file` на стороне платформы: процессы живут меньше 10 мс, новый поллер рассчитан именно на них.
- Как просмотрщик пользователя получает содержимое файла после `present_file` — в момент вызова файл в песочнице не читается.
- Что платформа делает с base64-выводом `read_file`: декодирование видно по результату, а кэширование или стадирация (как у `fetch_page` в Alibaba OSS, раунд 11) — нет.
- Точный порог TTL (между 16,4 мин и 49 мин), состав `POST /logs`, модель и failover, причина обрыва хода 14.10.

## Приложение Б. Программа инструмента `read_file` (дословно, 2846 символов)

Снята наблюдателем 17:13:20.411 (запись `cmdline_new`, id=4) — это полный текст командной строки процесса, включая тело heredoc. Ниже тот же текст; вторая запись (17:14:43.432, id=12, 2843 символа) отличается только значением `limit` (`2` вместо `None`).

```bash
/bin/bash -l -c python3 -I - <<'PY'
import base64
import codecs
import json
import os
import stat as stat_module
import sys

path = "/home/user/AuditArena/canary.db-wal"
offset = None
limit = None
max_bytes = 262144
half = max_bytes // 2

def emit(value):
    sys.stdout.write(json.dumps(value, separators=(",", ":")))
    sys.stdout.flush()
    sys.exit(0)

try:
    if not stat_module.S_ISREG(os.stat(path).st_mode):
        emit({"status": "open_error"})
    source = open(path, "rb")
except OSError:
    emit({"status": "open_error"})

start = 0 if offset is None else offset - 1
end = None if limit is None else start + limit
decoder = codecs.getincrementaldecoder("utf-8")("strict")
size = 0
newlines = 0
# The newlines before and inside the selection, and the selection state: 0 before, 1 inside, 2 after.
seen = 0
state = 1 if start == 0 else 0
selected = 0
head = bytearray()
tail = bytearray()

def take(data):
    global selected
    selected += len(data)
    if len(head) <= max_bytes:
        head.extend(data[: max_bytes + 1 - len(head)])
    if half > 0:
        tail.extend(data[-half:])
        if len(tail) > half:
            del tail[: len(tail) - half]

def end_of_newline(data, index, count):
    for _ in range(count):
        index = data.index(b"\n", index) + 1
    return index

with source:
    first = True
    while True:
        data = source.read(1024 * 1024)
        if not data:
            break
        if first:
            first = False
            if data.startswith(b"\xef\xbb\xbf"):
                data = data[3:]
        try:
            decoder.decode(data)
        except UnicodeDecodeError:
            emit({"status": "invalid_utf8"})
        size += len(data)
        newlines += data.count(b"\n")
        index = 0
        if state == 0:
            found = data.count(b"\n")
            if found < start - seen:
                seen += found
                continue
            index = end_of_newline(data, 0, start - seen)
            seen = start
            state = 1
        if state == 1:
            found = data.count(b"\n", index)
            if end is None or found < end - seen:
                take(data[index:])
                seen += found
            else:
                stop = end_of_newline(data, index, end - seen)
                take(data[index : stop - 1])
                state = 2

try:
    decoder.decode(b"", True)
except UnicodeDecodeError:
    emit({"status": "invalid_utf8"})

def b64(data):
    return base64.b64encode(bytes(data)).decode("ascii")

if selected <= max_bytes:
    emit({"status": "whole", "size": size, "lines": newlines + 1, "text": b64(head)})
emit(
    {
        "status": "elided",
        "size": size,
        "lines": newlines + 1,
        "selectedBytes": selected,
        "head": b64(head[: half + 1]),
        "tail": b64(tail),
    }
)
PY
```
