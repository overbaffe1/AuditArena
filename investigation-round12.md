## 2. Git-бутстрап дословно

**Reflog HEAD содержит ровно две записи платформы** и две мои:

```
0000000 → 59f0a99  user <user@e2b.local>                        1792243581  clone: from https://github.com/overbaffe1/AuditArena.git
59f0a99 → 7f14bf3  user <user@e2b.local>                        1792243582  checkout: moving from main to arena/404c5158-auditarena
7f14bf3 → 1dcec14  overbaffe1 <122226143+overbaffe1@users.noreply.github.com>  fetch -q origin … / reset: moving to FETCH_HEAD
```

- `.git/shallow` содержит **два** SHA — `59f0a99…` (верхушка `main`) и `7f14bf3…` (база сессии): мелкий клон `main` плюс мелкий fetch базового коммита. История — 1 коммит, `.git` занимает 152 КБ (33 свободных объекта и один pack).
- `.git/config`: для ветки сессии задан refspec **с завершающей звёздочкой** — `+refs/heads/arena/404c5158-auditarena*:refs/remotes/origin/arena/404c5158-auditarena*`; секция `[branch "main"]` есть, а для рабочей ветки **upstream не задан**. Отсюда видно, почему `git status` не показывает ahead/behind и почему push требует явного имени ветки.
- `[user] name = overbaffe1`, `email = 122226143+overbaffe1@users.noreply.github.com` прописываются платформой при каждом пересоздании. Следствие шире, чем в раунде 10: **даже локальный reflog атрибутирует мои операции пользователю** — записи `fetch` и `reset` этого хода сделаны от имени `overbaffe1`, хотя выполнял их агент. Записи самой платформы, наоборот, идут от `user <user@e2b.local>` — то есть до применения конфигурации репозитория.
- **Сверка содержимого.** После `git fetch origin arena/404c5158-auditarena` и `git reset --mixed FETCH_HEAD` рабочее дерево совпало с remote tip `1dcec14` полностью: `git status --porcelain -uall` пуст, `git diff --stat` — 0 строк. Значит, `git apply coding.patch` восстанавливает все девять файлов байт-в-байт. Это второй независимый тест гипотезы раунда 9 (первый дал 18 из 19 совпадений).
- **Побочный эффект, который я допустил:** мой `git fetch` перезаписал `.git/FETCH_HEAD`, где лежал артефакт fetch'а платформы. Содержимое утрачено. Урок метода: фиксировать артефакты до их изменения — в этом ходу я сначала сделал `reset`, и только потом читал `.git/logs` (к счастью, reflog перезапись FETCH_HEAD не затрагивает).

## 4. MMDS: метаданные песочницы читаются любым процессом

MMDS (Microvm Metadata Service) доступен по `169.254.169.254` и маршрутизируется через шлюз `169.254.0.22`, то есть отвечает сторона хоста (время ответа ~1 мс).

- Без токена все пути (`/`, `/latest/meta-data/`, `/mmds`, `/envs`, `/sandbox`, `/health`, `/metrics`) дают `401`: «No MMDS token provided. Use `X-metadata-token` or `X-aws-ec2-metadata-token` header to specify the session token.» — защита в стиле IMDSv2.
- **Штатный поток получения токена работает из-под обычного пользователя** (uid 1001, без `sudo` и без предварительных секретов): `PUT /latest/api/token` с заголовком `X-aws-ec2-metadata-token-ttl-seconds` → `200` и 48-символьный сессионный токен (base64-подобный; значение не печатаю). Я запросил TTL 300 с и получил токен; фактическое время жизни не проверял. Другие пути (`/api/token`, `/token`) → `404 Resource not found`.
- `GET /` с токеном возвращает список из четырёх ключей:

| Ключ | Значение | Комментарий |
|---|---|---|
| `accessTokenHash` | 128 hex-символов | SHA-512 токена envd; значение не печатаю |
| `address` | `http://192.0.2.1/logs` | адрес сборщика логов |
| `envID` | `mn0k6lgvyo6q8utbj8jh` | = `E2B_TEMPLATE_ID`: внутри инфраструктуры шаблон называется **env** |
| `instanceID` | `ijl99ttzvldua5zhggnpb` | = `E2B_SANDBOX_ID`: песочница — это **instance** |

- **Запись из гостя запрещена**: `PUT` нового ключа `arena-audit-readonly-probe` → `400 Invalid request.`, `DELETE` → `501`; после обеих попыток дерево осталось прежним (четыре ключа). Гость не может подменить свои метаданные — например, заменить `accessTokenHash`, чтобы заблокировать управляющий канал, или внедрить собственную конфигурацию.
- Отдельно проверено: traffic-токена границы (раунд 11) в MMDS нет — только четыре перечисленных ключа. Вывод раунда 11 подтверждён на уровне метаданных: материал для публичного доступа к портам песочницы внутрь не передаётся.

## 6. Аутентификация envd дословно: четыре пути без токена

`packages/envd/internal/api/auth.go` на закреплённом коммите (приведено с сокращениями: опущены строка журналирования и часть комментариев):

```go
// POST/init is secured via MMDS hash validation instead
var authExcludedPaths = []string{
        "GET/health",
        "GET/files",
        "POST/files",
        "POST/init",
}

func (a *API) WithAuthorization(handler http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, req *http.Request) {
                if a.accessToken.IsSet() {
                        authHeader := req.Header.Get(accessTokenHeader)   // "X-Access-Token"
                        allowedPath := slices.Contains(authExcludedPaths, req.Method+req.URL.Path)
                        if !a.accessToken.Equals(authHeader) && !allowedPath {
                                err := errors.New("unauthorized access, please provide a valid access token or method signing if supported")
                                jsonError(w, http.StatusUnauthorized, err)
                                return
                        }
                }
                handler.ServeHTTP(w, req)
        })
}
```

Отсюда следуют четыре вывода.

**1. Наблюдение раунда 11 получает точное объяснение.** Порт 49983 маршрутизируется из интернета, но без токена доступны только `GET /health` (поэтому снаружи пустой ответ `204`, который инструмент принял за ошибку) и `GET|POST /files` — они вынесены из-под проверки токена, потому что защищены подписью метода. Все остальные пути дают тот самый `401`.

**2. Подпись метода — предъявительская способность.** `generateSignature(path, username, operation, signatureExpiration)` строит строку `path:operation:username:tokenBytes` (и, если срок задан, добавляет `:expiration`), хеширует её SHA-256 и возвращает с префиксом `v1_`; операции — `read` и `write` (`SigningReadOperation`, `SigningWriteOperation`). Проверка на стороне сервера — `validateSigning`, её ошибка «missing signature query parameter» — ровно тот ответ, который я получил изнутри VM в раунде 7. **Если `signatureExpiration == nil`, срок в подпись не входит** ⇒ подписанный URL может быть бессрочным. Утечка такого URL (журналы, `Referer`, история браузера, публичный отчёт) даёт доступ к файлам песочницы в обход токена, а порт 49983, как установлено в раунде 11, достижим из интернета.

**3. Риск №18 раунда 11 снижается по тяжести.** Токен — 64 hex-символа, порождённые `crypto/rand` (256 бит энтропии), хранится в защищённой памяти и сравнивается константно по времени. В MMDS лежит только его SHA-512, поэтому подобрать токен по хешу практически невозможно. Реальная поверхность — `/health` (раскрытие живости песочницы по её идентификатору) и подписанные URL.

**4. Есть окно неаутентифицированного состояния.** Вся проверка обёрнута в `if a.accessToken.IsSet()`: пока токен не установлен, middleware пропускает **все** пути. Токен устанавливается через `POST /init` (`validateInitAccessToken`, ошибка `access token reset not authorized`), который защищён иначе — вызывающий должен предъявить токен, SHA-512 которого совпадает с `accessTokenHash` из MMDS; в `validateSigning` есть и прямая оговорка «no need to validate signing key if access token is not set». В текущем состоянии моей песочницы токен установлен (`GET /` → `401`, хеш в MMDS присутствует), а наблюдать окно задним числом из песочницы нельзя: оно приходится на первые мгновения после запуска envd.

## 7. Host-check предпросмотра выполняется изнутри песочницы

Зонд на `0.0.0.0:8091` зафиксировал единственный запрос — через 433 мс после `startedAt` из `meta.json` (13:47:28.245):

Host: 8091-ijl99ttzvldua5zhggnpb.e2b.app

Источник — loopback, версия `curl` совпадает с установленной в образе (`7.88.1-10+deb12u14`, `/usr/bin/curl`), заголовок `Host` — публичный URL порта. Следовательно, **проверка выполняется в самой песочнице и не проходит через границу E2B**. Это объясняет результат раунда 10 §7 (три «ломких» предпросмотра без предупреждений) и добавляет пятый случай: в ответ платформа записала `/tmp/.arena-hostcheck-8091` (тело `ok`) и `/tmp/.arena-hostcheck-headers-8091` (строка статуса и заголовки), а `warnings` снова пусты.

Вывод: механизм не может обнаружить проблемы, возникающие **за пределами** гостя, — требование `e2b-traffic-access-token` на границе (раунд 11), блокировку встраивания на стороне прокси, ошибки TLS. Он видит только тело и заголовки ответа локального сервиса. Для предпросмотра, который у пользователя открывается через `https://{port}-{sandboxId}.e2b.app`, этого недостаточно: локальный `200 OK` не гарантирует, что страница откроется в браузере.

## 8. Точка приёма телеметрии `http://192.0.2.1/logs`

Значение `address` из MMDS объясняет, куда смотрит `E2B_EVENTS_ADDRESS=http://192.0.2.1`: полный путь — `/logs`.

- `GET` и `OPTIONS` к `/logs` → `400 {"error":"method not allowed"}` ⇒ маршрут существует и принимает только другие методы.
- `GET` к `/`, `/health`, `/metrics`, `/events`, `/v1/events`, `/api`, `/debug`, `/version` → `404 {"error":"no matching operation was found"}` — характерная формулировка роутера на go-openapi: сервис знает только операции из своей спецификации.
- Спецификация не отдаётся: `/swagger.json`, `/openapi.json`, `/docs` → `404`.
- Ответы приходят за 1–4 мс ⇒ сервис на стороне хоста, а не внешний; адрес из документационного диапазона RFC 5737 выбран, видимо, намеренно, чтобы телеметрия не могла уйти в интернет даже при ошибке конфигурации.

`POST /logs` я не выполнял: это запись в журналы платформы. Сам факт канала важен: у любого процесса в песочнице есть исходящий путь к сервису приёма логов на хосте, и egress-фильтр его не блокирует.

## 9. Как исполняются инструменты платформы

`ps` по родителю показал: **процессы инструментов — прямые дети envd**. Во время этого хода в `/proc/1229/task/1229/children` и в выборке `ppid==1229` виден, например, `/bin/bash -l -c echo "=== …"` — мой текущий вызов bash. Родительских процессов-посредников между envd и командой нет.

Отсюда полезное следствие для метода: файл `/proc/1229/task/1229/children` перечисляет ровно те процессы, которые породила платформа. Это более точный и дешёвый способ наблюдения, чем перебор `/proc` в `tools/turn-end-watcher.py`, и он должен ловить даже короткоживущие процессы (сборщик патчсета живёт ~140 мс). Проверю в следующем раунде.

Ещё две детали этого хода:

- Каталог запуска фонового процесса по-прежнему содержит четыре файла (`meta.json`, `out.log`, `pid`, `run.cmd`), признака завершения нет. В `meta.json` видны `processId`, `name`, полный текст команды (включая переводы строк), `cwd` и `startedAt` в миллисекундах — `1792244848245`.
- Наблюдатель запущен с журналом **только в `/tmp`** (`ARENA_WATCH_REPO_LOG=0`, `/tmp/arena-watch-rev7.log`): зеркало в репозиторий стало опциональным, чтобы лог не попадал в патчсет и не цитировал сам себя (раунды 9–11).

## 11. Поправки к прошлым отчётам

1. **Раунды 7, 9, 10**: «пересоздание» описано точнее — это запуск новой песочницы **из базового шаблона** `mn0k6lgvyo6q8utbj8jh`, а не восстановление снимка сессии (§1).
2. **Раунд 10 §1**: «ID снимка не меняется при каждой паузе» — дополнение: короткие паузы возобновляют ту же песочницу и снимок, а после длинного зазора платформа стартует новую песочницу из базового шаблона (§1, §4, Приложение Б).
3. **Сводка сессии**: `10.12.0.8` — адрес хоста-оркестратора, а не песочницы; адрес песочницы всегда `169.254.0.21`. Пул хостов пополнен значением `.124` (§3).
4. **Раунд 7**: ответ `/files` «missing signature query parameter» объяснён из источника — это проверка подписи метода, а не аутентификационный middleware (§6).
5. **Раунд 11, риск №18**: тяжесть снижена — токен 256-битный случайный, в MMDS только его SHA-512; поверхность ограничена `/health` и подписанными URL (§6).
6. **Раунд 10 §7**: механизм `warnings` объяснён — host-check выполняется изнутри песочницы через loopback и не видит проблем границы (§7).
7. **Раунд 9**: «глобальный ignore не действует» — в этой песочнице `~/.config` отсутствует вовсе, вопрос снят (§1).
8. **Раунд 5**: netfilter пуст — подтверждено на новой песочнице, запущенной из базового шаблона (§3).
9. **Раунд 11 §2, вывод 3**: traffic-токена в песочнице нет — подтверждено и на уровне MMDS: в дереве только четыре ключа (§4).

## 12. Риски: обновление списка

**Новый №20 — MMDS доступен любому процессу в песочнице без привилегий.** Сессионный токен выдаётся по `PUT` без предварительных секретов, после чего читаются идентификаторы песочницы и шаблона, адрес сборщика логов и SHA-512 токена envd. Прямого вреда нет (хеш необратим при 256-битном токене, запись запрещена — `400`/`501`), но: любой сторонний код, запущенный в песочнице (например, скрипт сборки из чужого репозитория), получает готовые идентификаторы и хеш — а хеш служит оракулом для офлайн-проверки любых утёкших кандидатов в токены. Защита держится на том, что MMDS read-only, и на энтропии токена.

**Новый №21 — подписанные URL envd как предъявительские способности.** Подпись `v1_` + SHA-256 от `path:operation:username:token[:expiry]` выдаёт доступ к `GET|POST /files` без токена; срок действия не обязателен. В связке с публичной маршрутизацией порта 49983 (раунд 11) утечка одного такого URL означает внешний доступ к файлам песочницы. Рекомендация: всегда задавать `signature_expiration` и не публиковать подписанные URL.

**Новый №22 — окно неаутентифицированного envd до `POST /init`.** Пока токен не установлен, `WithAuthorization` пропускает все пути, а проверка подписи отключена. Установлено по исходникам; экспериментально не проверялось (окно приходится на первые мгновения жизни песочницы). В сочетании с публичной маршрутизацией 49983 это потенциально достижимая снаружи точка — оценить практически из своей песочницы не могу.

**Новый №23 — host-check предпросмотра не видит границу.** Проверка выполняется локальным `curl` через loopback, поэтому `warnings` не могут сообщить о требовании traffic-токена, о блокировке встраивания на прокси или об ошибке TLS (§7). Агент получает ложное подтверждение работоспособности предпросмотра.

**Снижен №18** (раунд 11): см. §6, вывод 3.

**Остаются в силе**: №11 (пустые пароли root/user и sshd внутри песочницы), №15 (атрибуция — теперь подтверждена и на уровне `.git/config` при каждом пересоздании, включая reflog), №16 (наблюдаемость), №19 (стадиирование ответов серверных инструментов в Alibaba OSS).

Отдельная заметка, не риск: у гостя есть исходящий канал к сервису приёма логов на хосте (`192.0.2.1/logs`, только не-GET методы). Возможность записи в телеметрию платформы из песочницы я не использовал и не проверял.
